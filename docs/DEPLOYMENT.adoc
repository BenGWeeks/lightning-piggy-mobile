== Deployment

This guide covers building, deploying, and distributing the Lightning Piggy mobile app.

=== CI checks

Every PR runs TypeScript, ESLint, Prettier, file-size and performance checks, plus an Android Metro development bundle export in parallel. Native builds run only when the native inputs listed in `.github/workflows/ci.yml` change, and always on pushes to main, tags, or manual dispatch. JavaScript-only PRs can get their fast merge signal in about five minutes; native changes still need the longer builds. Required checks remain configured in repository settings.

=== App Variants

Lightning Piggy supports three build variants, each with distinct identifiers so they can be installed side-by-side on the same device.

[cols="1,2,2,2", options="header"]
|===
| Variant | App Name | iOS Bundle ID | Android Package

| **Development**
| Lightning Piggy (Dev)
| `com.lightningpiggy.app.dev`
| `com.lightningpiggy.app.dev`

| **Preview**
| Lightning Piggy (Preview)
| `com.lightningpiggy.app.preview`
| `com.lightningpiggy.app.preview`

| **Production**
| Lightning Piggy
| `com.lightningpiggy.app`
| `com.lightningpiggy.app`

|===

Variants are selected via the `APP_VARIANT` environment variable in `app.config.ts`. Each variant shares the same white PiggyBank-and-bolt mark on its own radial-gradient background so the installs are easy to tell apart: production is pink, development is blue and preview is purple. The iOS icon (`assets/icon.png`, `icon-dev.png`, `icon-preview.png`) bakes the gradient in; on Android the gradient is the adaptive-icon `backgroundImage` (`assets/android-icon-background[-dev|-preview].png`) behind the shared `android-icon-foreground.png`, with a solid `backgroundColor` per variant (`#D6007E` / `#3F86C9` / `#8B5CF6`) set alongside it.

The icon PNGs (plus `android-icon-monochrome.png` and `favicon.png`) are generated by `scripts/generate-app-icons.sh`, which requires ImageMagick (`convert`). To change colours, sizes or the mark, edit the tweakables at the top of the script, run `bash scripts/generate-app-icons.sh` and commit the regenerated PNGs. SVG rasterisation can differ slightly between ImageMagick versions and renderers, so expect minor pixel differences when regenerating on a different machine.

=== Local Builds

[source,bash]
----
# Development build for Android — Metro-dependent, for active JS hacking
APP_VARIANT=development npx expo run:android

# Production-like build via Expo (convenience wrapper)
npx expo run:android
----

==== Dogfooding: local production build → physical Android device (fast loop)

When you want to ship a working release to your own device **without**
cutting a formal GitHub Release (TestFlight / Play are not yet wired,
and the phone already has an EAS-signed `com.lightningpiggy.app`
install you don't want to lose data on):

[source,bash]
----
# Build locally but with EAS's production keystore, so the APK is
# sig-compatible with whatever's already on the phone. APK lands at
# android/app/build/outputs/apk/release/app-release.apk.
#
# EXPO_NO_DOCTOR=1 skips the pre-flight version-compatibility checker
# which is noisy on minor-mismatch deps and not relevant to signing.
#
# TMPDIR="$HOME/eas-tmp" is REQUIRED on hosts with /tmp on tmpfs
# (default Ubuntu/Debian setup, 12 GB cap). The EAS local builder
# generates ~9 GB of native-lib intermediates during the multi-arch
# APK assembly (arm64 + armv7 + x86 + x86_64), and Gradle crashes with
# `UncheckedIOException: Could not add entry ... to cache fileHashes.bin`
# the moment tmpfs hits 100 %. Pointing TMPDIR at disk-backed storage
# gives Gradle the ~10 GB of headroom it needs. ($HOME instead of ~ is
# unambiguous across shells / non-interactive runners.)
mkdir -p "$HOME/eas-tmp"
TMPDIR="$HOME/eas-tmp" EXPO_NO_DOCTOR=1 eas build --local --platform android --profile production --non-interactive

# Install over the existing app — preserves user data (Nostr nsec,
# wallet pairings, conversation cache).
adb -s <serial> install -r android/app/build/outputs/apk/release/app-release.apk
----

Build time: ~10-15 min fresh, ~2-3 min on a warm gradle cache. No
cloud queue, no Metro, no fresh-login required on the device.

If the build fails partway with `UncheckedIOException: Could not add
entry ... fileHashes.bin` (or any I/O error inside the Gradle cache),
check `df -h /tmp` first — if it's at or near 100 % the
`TMPDIR="$HOME/eas-tmp"` knob above is what you're missing. The
`$HOME/eas-tmp` working tree can be deleted between builds
(`rm -rf "$HOME/eas-tmp"`) to reclaim disk; the next `mkdir -p` and
Gradle will re-create everything (including hidden entries like
`.gradle`) before the next build.

===== Verify the install actually committed

`adb install -r` can print `Performing Streamed Install / Success`
for the file-transfer phase even when the install-commit is
rejected. Always tail the **full** adb output (not `tail -3`), and
cross-check the on-device state:

[source,bash]
----
# Confirm lastUpdateTime is now (not hours ago) + versionCode matches
# what you just built. If lastUpdateTime hasn't moved, the install
# DIDN'T land — check for INSTALL_FAILED_* lines in the adb output.
adb -s <serial> shell dumpsys package com.lightningpiggy.app | \
  grep -E "versionCode|lastUpdateTime"
----

===== Connecting the phone for sideload

`adb` first needs to see the phone. USB is the happy path, but in practice the dog-eared cable or a stuck USB controller often defeats it — when that happens, fall back to wireless adb instead of debugging the cable. Both phone and laptop must be on the same Wi-Fi.

*Diagnose USB before giving up:*

[source,bash]
----
# Check USB enumeration at the kernel level — this works without
# adb authorization, so it's a clean signal of cable / port health.
# A working Pixel shows up as `Bus NNN Device NNN: ID 18d1:...`
# (Google vendor ID 18d1).
lsusb | grep -iE "google|18d1"

# If lsusb is empty even after re-plugging, the laptop doesn't see
# the phone at all — it's the cable, the port, or lint in the
# phone's USB-C socket. Don't keep poking adb; switch to wireless.
----

*Wireless adb (Android 11+ — Pixel 8 supports it):*

. *Phone:* Settings → System → Developer options → Wireless debugging → ON.
. *Phone:* tap the *Wireless debugging* row (not just the toggle) to open the detail page.
. The detail page shows an **IP address & Port** at the top — this is the **persistent connection port** (no code beside it). Note it.
. Tap *Pair device with pairing code* to open a dialog that shows a *different* port + a 6-digit code. Both expire after one pairing attempt — pair codes are one-shot, so don't generate one until the laptop is ready to consume it.
. *Laptop:* pair, then connect:
+
[source,bash]
----
adb pair 192.168.1.18:<PAIR_PORT> <CODE>
# Successfully paired ... [guid=adb-...]

adb connect 192.168.1.18:<CONNECT_PORT>
# connected to 192.168.1.18:<CONNECT_PORT>

adb devices
# 192.168.1.18:<CONNECT_PORT>   device
----
. From here on, every `adb` command takes `-s 192.168.1.18:<CONNECT_PORT>` (the wireless socket) as the device serial — substitute that for `-s <serial>` in the commands above.

*Common gotchas:*

* `adb pair` returns `error: protocol fault (couldn't read status message): Success` — the pair code was already burned (one-shot, expires on any failed handshake). Tap *Pair device with pairing code* again to generate a new code.
* `adb connect` succeeds but `adb devices` shows the host as `offline` — you skipped pairing. Pair first, *then* connect.
* `adb mdns services` is empty even after pairing — your Wi-Fi blocks multicast (common on guest networks and some routers). Manual pair + connect with explicit IPs still works; only mDNS auto-discovery is broken.
* The connect port and the pair port are *different* — the connect port is shown on the main *Wireless debugging* page; the pair port appears only inside the *Pair device with pairing code* dialog. Don't try to connect to the pair port; you'll get `offline`.

==== Why `./gradlew assembleRelease` + `adb install -r` silently fails

Running `cd android && ./gradlew :app:assembleRelease` directly works
*and* produces a smaller/faster build — but the APK is signed with
the local `android/app/debug.keystore`, NOT the EAS-managed keystore
that produced the install currently on your Pixel. Different
signatures → Android rejects the install as
`INSTALL_FAILED_UPDATE_INCOMPATIBLE`, with no way to `-r` over it
short of uninstalling (which wipes user data).

Three options if you really want gradle-direct builds in the loop:

1. **Use `eas build --local`** (above) — slower but keystore-correct.
2. **Download the EAS production keystore locally once** via
   `eas credentials -p android`, point `signingConfigs.release` at
   it in `android/app/build.gradle`. Subsequent `./gradlew
   :app:assembleRelease` runs produce EAS-signed APKs. Keystore file
   must not be committed (`*.jks` is already in `.gitignore`).
3. **Uninstall and reinstall** — loses data on the target device.

Running `./gradlew assembleRelease` + `adb install -r` can appear
to succeed while leaving the previous install in place, so
subsequent tests may still be exercising the pre-fix app. Verify
`lastUpdateTime` after install, or use `eas build --local`.

=== Release workflow

Releases are cut by publishing a **GitHub Release** (which creates the tag server-side and fires `.github/workflows/release.yml`). The workflow:

1. Runs quality gates (typecheck / lint / format-check).
2. Kicks off EAS production builds for both platforms. **iOS** is auto-submitted to TestFlight via EAS's ASC API key. **Android** is built only — no auto-submit to Play Internal until the Google Play Developer account + service-account JSON are wired up via `eas credentials` (see the "Android Distribution — Google Play Internal Testing" section below). The Android APK is attached to the GitHub Release instead, so testers can sideload it immediately.
3. Downloads the resulting Android APK from EAS and attaches it as `lightning-piggy-<tag>.apk` on the Release page for sideloading.
4. Regenerates `docs/TECHNICAL_SOLUTION_DOCUMENT.pdf` from the AsciiDoc sources and attaches that too.

==== Version numbering

The user-visible `X.Y.Z` lives in `package.json` and is read at config time by `app.config.ts` (`version: pkg.version`). One source of truth across all build paths — local `eas build`, GitHub Release publish, `workflow_dispatch` re-runs all read the same value. To bump:

[source,bash]
----
npm version patch          # 1.0.0 → 1.0.1
npm version minor          # 1.0.0 → 1.1.0
npm version major          # 1.0.0 → 2.0.0
npm version 1.2.3          # explicit
git push origin main --follow-tags
----

`npm version` does three things atomically: writes `package.json`, creates a git commit (`1.0.1`), and creates a tag (`v1.0.1`). Pushing the tag triggers the release workflow if you also publish a GitHub Release for it.

The build number (iOS `CFBundleVersion` / Android `versionCode`) is independent — EAS auto-increments a remote counter on every production build (`eas.json` → `"appVersionSource": "remote"` + `"autoIncrement": true`). It's monotonic, never reused, and not tracked in-repo.

[cols="1,2,3", options="header"]
|===
| Number | Source | Notes

| `X.Y.Z` (user-visible version)
| `package.json` "version"
| Bump with `npm version <patch\|minor\|major\|x.y.z>`. Read by `app.config.ts` → applied to iOS `CFBundleShortVersionString` + Android `versionName`. **Don't hand-edit `package.json`** — use `npm version` so the commit + tag stay in sync.

| Build number (iOS) / `versionCode` (Android)
| EAS remote counter
| Auto-bumps per production build. Independent of `X.Y.Z`. Visible in TestFlight as `1.0.0 (13)` — the `(13)` is the counter.

| The `android.versionCode:` field in `app.config.ts`
| Hand-edited per **local** prod build (see "Local production builds" below)
| Floor for the **locally-built** Android `versionCode`. EAS production builds use the **remote** counter and ignore this field. Bump this manually before each local `--variant release` install whenever the target device already has a higher versionCode installed (e.g. from a prior EAS build).
|===

NOTE: The pre-`npm version` flow had `app.config.ts` hardcoded to `'1.0.0'` and a `sed` step in `release.yml` that overwrote it from the tag — but the sed only ran on actual GitHub Release events, so `workflow_dispatch` re-runs and local `eas build` invocations always shipped `1.0.0` regardless of the tag. The current flow eliminates that drift.

==== Installing on an iPhone that can't use TestFlight (family members under 13)

TestFlight requires an Apple ID aged 13+, so younger family members get the production app as a *device-signed* (ad-hoc) build instead. The `production-adhoc` profile in `eas.json` is the production app (same bundle id, same notification server) signed for the registered devices only.

. Register the phone once: `eas device:create` (interactive: choose *Website*, open the link on the phone, install the profile). Plugging the phone into a Mac and running an Xcode build with `-allowProvisioningDeviceRegistration` also registers it.
. Check out the release tag in a tag-specific worktree: `git worktree add --detach ../lp-adhoc-vX.Y.Z vX.Y.Z && cd ../lp-adhoc-vX.Y.Z` (remove it afterwards with `git worktree remove ../lp-adhoc-vX.Y.Z`; reusing one path fails once it's registered). Before building, check that the tag's `eas.json` contains `production-adhoc` with `"environment": "production"`. Older tags such as `v1.5.0` lack this profile: add the following entry under `build` in that detached worktree's `eas.json`, preserving the tag's other profiles and app source. This is a local build-configuration change; do not move the release tag.
+
[source,json]
----
"production-adhoc": {
  "extends": "production",
  "environment": "production",
  "distribution": "internal",
  "autoIncrement": false
}
----
+
The explicit environment selects the same EAS variables as the store production build; internal distribution otherwise defaults to the preview environment.
. Build: `eas build -p ios -e production-adhoc`. The first run must be *interactive* (it creates the ad-hoc provisioning profile and asks which devices to include; pick all). Later runs work with `--non-interactive`; after registering a *new* phone, add `--refresh-ad-hoc-provisioning-profile` so the profile is regenerated to include it (a non-interactive build otherwise reuses the existing profile, which won't install on the new phone). Apple authentication can use the App Store Connect API key via `EXPO_ASC_API_KEY_PATH`, `EXPO_ASC_KEY_ID`, `EXPO_ASC_ISSUER_ID` instead of an Apple ID login.
. Install: open the build page's install link on the phone (Safari), or over a cable from a Mac: `curl -L -o app.ipa <artifact url>` then `xcrun devicectl device install app --device <id> app.ipa` (`xcrun devicectl list devices` shows the id). The phone needs *Developer Mode* on (Settings → Privacy & Security) and must trust the Mac.

The build doesn't auto-update: repeat steps 2–4 for each release the phone should get. `autoIncrement` is off so the build number doesn't advance the release counter.

== Local production builds (fallback)

WARNING: **This is not the release path.** Cutting a release goes through `.github/workflows/release.yml` (see "Cutting a release" below), which runs EAS cloud builds anchored to the published tag. Running `eas build --local` manually for a release detaches the artifact from any published tag — the build comes from the local checkout snapshot whenever you happened to invoke it, with no record of which source revision actually shipped. The GitHub Release notes then drift away from what's in users' hands. We hit exactly this on v1.1.0 (the local build artifact wasn't anchored to the tag, and reconstructing what the binary contained meant inspecting working-tree state after the fact).

The fallbacks below are for two narrow cases:

. **Sideloading a release-flavor APK to a device for testing** — usually for R8 / proguard validation. Prefer pulling the latest **production-profile** cloud-built APK instead: list with `eas build:list --platform android --profile production --status finished --limit 1`, then download the artifact by its build URL/ID (not `--latest`, which isn't profile-constrained and may hand back a `development` / `preview` APK with the `.dev` / `.preview` applicationId — that won't upgrade a production install). Only fall back to a local build when you're offline or the EAS queue is jammed.
. **Reproducing a release-build issue locally** — e.g. a class got stripped and you need to bisect Gradle config.

===== Case 1 (offline fallback): keep existing data on an EAS-built device

NOTE: The **recommended** path is to download a cloud-built production APK (see the bullet above) — it's already signed with the EAS upload keystore and needs no `versionCode` bookkeeping. Reach for the local build below only when you're offline or the EAS queue is jammed.

Use `eas build --local --profile production`. This runs **EAS's production pipeline** on your machine — it fetches the EAS upload keystore at build time so the APK signature matches your existing install, and emits a sideload-able `.apk`:

[source,bash]
----
# Builds an .apk in the repo root (e.g. build-1733864000123.apk) without
# installing. The signing keystore comes from EAS — that's what makes
# the APK a valid upgrade for an existing EAS-installed app.
eas build --local --profile production --platform android --non-interactive

# Then sideload to the Pixel. `adb -s` takes the adb serial here (NOT
# the model name expo run:android wants).
adb -s <serial> install -r build-*.apk
----

Side-loading this way preserves all app data (`/data/data/com.lightningpiggy.app/` is left untouched on upgrade). Wallets, Nostr login, message history all survive.

**Important: bump `versionCode` in `app.config.ts` *before* the build.** `appVersionSource: "remote"` in `eas.json` only affects EAS *cloud* builds — `eas build --local` reads `versionCode` directly from `app.config.ts`, just like `expo run:android --variant release` does. So if the cloud counter has run ahead of the local floor (which it always does after a few cloud releases), the locally-built APK gets a number behind the device's installed version and `adb install -r` rejects it:

[source]
----
INSTALL_FAILED_VERSION_DOWNGRADE: Update version code N is older than current M
----

Workflow:

. Check the latest cloud-built versionCode: `eas build:list --platform android --status finished --limit 1`
. Bump `android.versionCode` in `app.config.ts` to **(latest-EAS) + 1** (commit this — the bump persists harmlessly across releases since the cloud pipeline ignores it)
. Run `eas build --local --profile production` and sideload the resulting APK

Caveats:
* First run can be slow — eas-cli has to fetch the keystore + run a clean Gradle build (~5–10 min). Subsequent runs are incremental.
* Local builds do *not* burn the EAS cloud counter; only cloud builds (`eas build --profile production` without `--local`) increment that.

===== Case 2: standalone local prod build (fresh device or OK to wipe data)

`npx expo run:android --variant release --device <Pixel_model>` produces a locally-signed prod APK. **The signing keystore differs from the EAS upload keystore**, so this APK *cannot* upgrade an existing EAS-built install — Android refuses cross-keystore updates with:

[source]
----
INSTALL_FAILED_UPDATE_INCOMPATIBLE: Existing package signatures do not match newer version
----

The `-r -d` flags don't bypass this; it's a security guarantee, not a flag. Either `adb uninstall com.lightningpiggy.app` first (wipes data), or use Case 1.

A second gotcha: the locally-built versionCode does not auto-increment. The local pipeline reads `android.versionCode` from `app.config.ts` directly — so a device under test that's running an EAS-built versionCode well ahead of the local floor rejects the install:

[source]
----
INSTALL_FAILED_VERSION_DOWNGRADE: Update version code N is older than current M
----

Workflow if you do go this route:

. Read the most recent EAS-built versionCode:
+
[source,bash]
----
eas build:list --platform android --status finished --limit 1
----
. Bump `android.versionCode` in `app.config.ts` to **(latest-EAS) + 1**. The release workflow overwrites `version:` but not `versionCode:`, so this bump persists across releases. EAS uses its own remote counter regardless, so committing this number doesn't interfere with the cloud pipeline.
. Re-prebuild + build:
+
[source,bash]
----
APP_VARIANT=production npx expo prebuild --platform android --no-install
npx expo run:android --variant release --device <Pixel_model>
----
+
`--device` for physical phones takes the **model name** (`Pixel_8`), not the adb serial. For emulators it's the AVD name. Maestro CLI is the opposite — it accepts the adb serial. See `docs/TROUBLESHOOTING.adoc`.
. Uninstall first if the device has an EAS-built install (signature mismatch, see above): `adb -s <serial> uninstall com.lightningpiggy.app`.

===== Reading the installed versionCode + signature

[source,bash]
----
# Currently-installed version
adb -s <serial> shell dumpsys package com.lightningpiggy.app \
  | grep -E "versionCode|versionName"

# Currently-installed signature (SHA-256 of the signer's cert).
# An EAS-built install and a locally-built install will print
# different fingerprints here — that's the source of the
# UPDATE_INCOMPATIBLE error.
adb -s <serial> shell dumpsys package com.lightningpiggy.app \
  | grep -E "Signer #1 cert"
----

Reading the version of a running install:

* iOS: *Settings → General → About → Lightning Piggy* shows `X.Y.Z (buildNumber)`.
* Android: `adb -s <serial> shell dumpsys package com.lightningpiggy.app | grep -E "versionCode|versionName"`.

Reading the latest build number from EAS without installing:

[source,bash]
----
eas build:list --platform android --status finished --limit 1 \
  | grep -E "^Version|^Build number"
----

==== Cutting a release

**Always go through this workflow — never run `eas build` manually for a release.** The workflow tags first then builds, so artifacts are anchored to one commit; manual / local builds aren't tied to a published tag, so there's no record of which source revision actually shipped and the GitHub Release notes drift away from the binary in users' hands (v1.1.0 hit this — the local build artifact wasn't anchored to the tag).

. **Bump the version locally first** — `npm version <patch|minor|major|x.y.z>` writes `package.json`, creates a commit, and tags `vX.Y.Z` atomically. Push it: `git push origin main --follow-tags`.
. Go to https://github.com/LightningPiggy/lightning-piggy-mobile/releases → *Draft a new release*.
. Choose a tag like `v1.0.1` (create on publish) targeted at `main`. **The tag is the source of truth for the user-visible version** — the workflow strips the leading `v` and writes it into `package.json` via `npm version --no-git-tag-version`. `app.config.ts` reads `version: pkg.version`, so iOS `CFBundleShortVersionString`, Android `versionName`, and the in-app version label (drawer + About screen, via `src/utils/appVersion.ts`) all flow from that single value. Pre-release suffixes (e.g. `v1.0.0-rc1`) are stripped to keep the store-facing version a strict `X.Y.Z`.
. Write release notes, click *Publish release*.
. Watch *Actions → Release*. When it finishes, the Release page has the APK and PDF attached; TestFlight has the iOS build (auto-distributed to the Public Beta external group via `eas.json` `submit.production.ios.groups`).
. *What to Test* fills itself in — the `set-testflight-whats-new` workflow job uses the generated PR-title notes, polls App Store Connect for the just-submitted build, and PATCHes the localisation via `scripts/asc-set-whats-new.mjs` (see "TestFlight 'What to Test' notes" below). Manual pasting is only needed when the `EXPO_ASC_API_KEY_ID` / `EXPO_ASC_API_KEY_ISSUER_ID` / `EXPO_ASC_API_KEY_P8` secrets aren't configured.
. *Zapstore* follows on its own: `release-zapstore.yml` publishes the attached APK, signed by the Lightning Piggy account (see "Zapstore (Nostr App Store)").

NOTE: `versionCode` (Android) and `buildNumber` (iOS) are managed by EAS's remote counter (`eas.json` → `"appVersionSource": "remote"` + `"autoIncrement": true`). Don't hand-edit them for releases — cloud builds auto-increment past whatever's in `app.config.ts`. The integer in the file is only the floor for `eas build --local` and `expo run:android --variant release`, both of which are dev-test paths, not release paths.

`npm version` accepts pre-release suffixes too: `npm version 1.0.1-rc1` → tag `v1.0.1-rc1`, `package.json` `1.0.1-rc1`. `app.config.ts` reads `package.json` verbatim; if you ship a non-strict-X.Y.Z value, Apple's validator will reject the upload (`CFBundleShortVersionString` must be three numeric components separated by dots). For RC builds, prefer bumping `package.json` to the *target* X.Y.Z and using the GitHub Release page's "Pre-release" checkbox to mark it as such.

==== Publishing the release note to Nostr (Amber)

`.github/workflows/release-nostr-note.yml` publishes a kind-1 announcement from BenGWeeks when a stable GitHub Release is published. It generates notes from PR titles in the release tag range and includes Android, TestFlight and website install links. A manual dispatch can publish any existing release tag, including prereleases.

Ben's account key stays only in Amber. `nostr-tools/nip46`'s `BunkerSigner` uses `NOSTR_RELEASE_CLIENT_KEY`, a separate stable client key, to request remote signing through `NOSTR_RELEASE_BUNKER_URI`. `nak` v0.21's `event --help` and global help expose no stable client-key option for bunker signing, so the Node client supplies it explicitly. The runner verifies Ben's public key, the signature and every event field before publishing.

Follow link:../scripts/release-note-bunker-setup.md[the one-time Amber setup helper] for the exact hidden-input commands: `nak key generate` pipes directly into `gh secret set NOSTR_RELEASE_CLIENT_KEY`; Amber's bunker URI is read without echo and piped into `gh secret set NOSTR_RELEASE_BUNKER_URI`. Never use or export Ben's account private key. Keep the client secret unchanged across releases so Amber recognises the connection.

Open Amber to approve the connection and kind-1 request (or configure remembered per-kind approval). The workflow waits up to ten minutes. It fetches Ben's latest kind-10002 relay list from `purplepag.es`, `relay.primal.net` and `user.kindpag.es`, publishes to write/unmarked relays, and requires two acceptances. If none are found, the fallback is `relay.primal.net`, `relay.damus.io` and `nos.lol`. A successful run appends `https://njump.me/<nevent>` to the Release body. Missing secrets emit a notice and skip; the app release workflow runs independently.

Preview locally without secrets or network:

[source,bash]
----
node scripts/build-release-note.mjs --tag v1.4.1
npm run test:release-note
----

Re-run via *Actions → Release Nostr note → Run workflow* with `tag=v1.4.2`, selecting the default branch, or:

[source,bash]
----
gh workflow run release-nostr-note.yml --repo LightningPiggy/lightning-piggy-mobile --ref main -f tag=v1.4.2
----

NOTE: Dispatch publishes a real note and can create a duplicate on retry. Check the Release body first. APK and TestFlight builds run separately and may not yet be ready when the note is published. ==== Build and submit

[source,bash]
----

CAUTION: The App Store Connect *app-record creation* step still requires interactive Apple ID login (API keys cannot create new apps). Do the one-time record creation in the browser, not via EAS, and you avoid the Apple ID flow entirely afterwards.

==== TestFlight "What to Test" automation

`eas build --auto-submit` ships a build to TestFlight with a blank *What to Test* field — `eas.json` has no slot for it (as of EAS CLI 18) and the underlying `eas submit` does not expose the App Store Connect `betaBuildLocalizations` endpoint either. The release workflow's `set-testflight-whats-new` job fills it in post-submit, using the same generated notes as the GitHub Release.

===== Release notes

PR titles are the source of release notes. Use Conventional Commits and imperative, user-facing wording for `feat` and `fix`. `scripts/release-notes-from-prs.sh <from-tag> <to-ref>` lists PRs merged into main between the tags and groups `feat` under *New*, `perf` / `refactor` under *Improved*, and `fix` under *Fixed*, with PR numbers. Other types are omitted. Contributors do not edit a shared notes file.

The release workflow appends generated notes below any human-written GitHub Release notes and uses the same text for TestFlight (capped at 3 900 characters). It appends the generated section to the existing changelog archive and attaches the cumulative `CHANGELOG.md` to the Release, carrying forward the previous release's archive. It creates no reset commit or post-release PR.

The TestFlight job calls App Store Connect's `PATCH /v1/betaBuildLocalizations/{id}` in every applicable locale. Once Apple processes the build, it submits it for Beta App Review unless already submitted. Review submission failures warn without failing the release; set `ASC_SKIP_REVIEW=1` to skip review submission. If no qualifying PRs are found, notes default to `Bug fixes and improvements.`

===== One-time GitHub Secrets setup

The job needs the App Store Connect API key (the same `.p8` EAS uses for `eas submit` — but the `.p8` itself lives only on EAS's server, so you have to register it as a GitHub secret too). These are the **`EXPO_ASC_*`** secrets — likely already present (EAS uses the same key), so check *Settings → Secrets and variables → Actions* before re-adding:

[cols="1,3", options="header"]
|===
| Secret | Value

| `EXPO_ASC_API_KEY_ID`
| The 10-character key identifier from App Store Connect → *Users and Access* → *Integrations* → *Team Keys* (e.g. `ABC1234567`). Same value as `ascApiKeyId` in the `eas.json` snippet above.

| `EXPO_ASC_API_KEY_ISSUER_ID`
| The team's issuer UUID, shown above the key list on the same page (e.g. `00000000-0000-0000-0000-000000000000`). Same as `ascApiKeyIssuerId`.

| `EXPO_ASC_API_KEY_P8`
| The full PEM contents of the `AuthKey_XXXXXXXXXX.p8` file, including the `-----BEGIN PRIVATE KEY-----` / `-----END PRIVATE KEY-----` lines. Paste the file contents verbatim into the secret value box; GitHub preserves the newlines.
|===

The numeric App ID (`ASC_APP_ID`) is hard-coded in the workflow because it matches `ascAppId` in `eas.json` and never changes for a given app record.

If any of the three secrets is unset, the job emits a `::warning` and skips silently — the release still succeeds, you just have to fill in *What to Test* by hand for that build via App Store Connect.

===== Why a separate ASC API call (not just an EAS flag)

`eas submit` uses Apple's `pilot` (fastlane) under the hood, which does accept a `changelog` argument — but EAS doesn't surface it through `eas.json` or `eas submit --changelog`. Until Expo wires that through, the post-submit ASC PATCH is the cleanest option that works with `--auto-submit`. Two pieces of code do the work:

* `scripts/release-notes-from-prs.sh` — groups merged PR titles for the release tag range.
* `scripts/asc-set-whats-new.mjs` — generates an ES256-signed JWT, polls `/v1/builds` until the just-uploaded build appears in App Store Connect (Apple typically takes 5–15 min after EAS reports the submit complete), then PATCHes the localisation.

The polling loop in the second script is bounded by `ASC_MAX_WAIT_SECS` (default 900 s = 15 min). If Apple's processing queue is unusually backed up and the build hasn't appeared in time, the script exits 0 with a warning so the release isn't gated on Apple's queue depth — re-run the same script locally with the same env vars to fill it in once the build is visible.

=== iOS Distribution — Ad-hoc (sideload)

Ad-hoc distribution installs a signed IPA onto a specific iPhone without going through TestFlight or the App Store. Use it when:

* The tester is **under 13** (Apple blocks them from TestFlight's terms).
* You want to install a build immediately without waiting for Apple's Beta App Review or TestFlight processing.
* The build will only run on a small, known set of devices (ad-hoc profiles cap at 100 registered device UDIDs per product category — iPhone, iPad, etc. — per Apple Developer membership year).

==== How it works

* EAS builds an IPA signed with an **ad-hoc provisioning profile** that has specific **device UDIDs** baked in at signing time.
* The IPA only installs on iPhones whose UDID is in that profile. Every new tester requires re-signing (or a fresh rebuild) after their UDID is registered.
* Unlike TestFlight, there's no age check — this is an Apple-sanctioned developer distribution channel, not a consumer beta programme.

==== One-time Apple Developer Portal setup

. Register the preview bundle ID at https://developer.apple.com/account/resources/identifiers[developer.apple.com/account/resources/identifiers]:
+
* **Identifier type:** App IDs → App
* **Description:** `Lightning Piggy Preview`
* **Bundle ID (Explicit):** `com.lightningpiggy.app.preview`
* **Capabilities:** match the production bundle ID's capability set. Today the only iOS-side capability the app declares (per `ios/.../*.entitlements`) is **NFC Tag Reading** — tick that box. Other permissions (camera, contacts, microphone, photos) are handled via Info.plist usage strings, not capabilities, so they don't need toggling here.
+
(The production bundle ID gets auto-registered by EAS on the first iOS build, but the preview variant needs manual registration because the ad-hoc build path doesn't auto-create it. Missing the NFC capability surfaces as a confusing fastlane failure mid-build: `Provisioning profile ... doesn't include the NFC Tag Reading capability` / `... doesn't include the com.apple.developer.nfc.readersession.formats entitlement`. Fix is to enable it on the identifier and re-run the build — EAS auto-regenerates the provisioning profile.)

. Register each tester's device UDID once via `eas device:create`:
+
[source,bash]

This produces a single reusable URL. Send it to every tester — they open it in Safari on their iPhone, tap *Download Profile*, then *Settings → General → VPN & Device Management* → install the profile. Their UDID is then reported back to your Apple team automatically.

=== Zapstore (Nostr App Store)

https://zapstore.dev[Zapstore] is a permissionless Android app store built on Nostr. Nobody has to approve a listing. Users zap the developer directly, and the app checks each release's signature and APK hash before it installs. Every stable GitHub Release is published there automatically: https://zapstore.dev/apps/com.lightningpiggy.app.

==== How it works

* **`zapstore.yaml`** (repo root) is the listing: name, summary, description, icon (`assets/icon.png`), screenshots (`docs/images/app-*.webp`), links, licence, supported NIPs, and the publishing `pubkey`. `relay.zapstore.dev` whitelists a new publisher by fetching this file from the repository and matching the `pubkey`, so it must be on `main` before the first publish. Listing edits take effect with the next release.
* **`.github/workflows/release-zapstore.yml`** runs when the *Release* workflow completes (or by hand with a tag). It is separate from `release.yml`, so a Zapstore or signer problem never blocks a release. It skips, with a notice, prereleases, drafts, releases without `lightning-piggy-vX.Y.Z.apk` attached, and runs where the secrets are missing. Then it:
.. installs the pinned https://github.com/zapstore/zsp[zsp] (`ZSP_VERSION`, binary checked against `ZSP_SHA256`);
.. pins the tag: copies `zapstore.yaml` to `.zapstore-ci.yaml` and appends `release_filter: '^vX\.Y\.Z$'`, because zsp otherwise publishes the newest GitHub Release;
.. runs `zsp publish --check`, a read-only fetch and parse of the APK;
.. runs `scripts/zapstore-signer-preflight.mjs`, which installs the stable NIP-46 client key where zsp looks for it (`$XDG_CONFIG_HOME/zsp/bunker-keys/<bunker pubkey>.key`). It first requests the public key to reuse an already authorised client without resending the one-time pairing secret. If that fails or gets no answer within 10 seconds, it pairs the client, then checks the account even if the signer reports "already connected". It refuses to continue unless the bunker signs for the Lightning Piggy account. It waits up to **30 minutes** for the connection to be approved: ten minutes timed out twice for the release note;
.. passes zsp a bunker URI with the `secret` parameter removed via `SIGN_WITH`: the pre-flight has already paired the stable client key, so zsp must not resend the consumed token;
.. runs `zsp publish --quiet --skip-metadata`. zsp downloads the APK, uploads it with the icon and screenshots to `cdn.zapstore.dev` (Blossom), and publishes to `wss://relay.zapstore.dev`.
* **Events signed by the Lightning Piggy account:** kind `32267` (app), `30063` (release, `d` = `com.lightningpiggy.app@X.Y.Z`), `3063` (APK asset: SHA-256, size, `apk_certificate_hash`, platforms), and one kind `24242` Blossom upload authorisation per uploaded file (icon, 5 screenshots, APK). That makes 10 signatures per release.
* **The signer is the Lightning Piggy team account**, `npub1y2qcaseaspuwvjtyk4suswdhgselydc42ttlt0t2kzhnykne7s5swvaffq` (hex `22818ec3…5a79f429`). Richard holds its key. The kind-1 release announcement (see "Publishing the release note to Nostr (Amber)") still comes from Ben's own account, unchanged.
* **Re-runs are safe.** If the version is already on the relay for this account, zsp reports nothing to do and exits.

==== Who signs owns the listing

Whoever signs the first release for `com.lightningpiggy.app` owns the Zapstore listing. Releases from any other key look like a different publisher. Two guards keep that the Lightning Piggy account: zsp refuses a local signer that doesn't match `zapstore.yaml`'s `pubkey`, and the workflow pre-flight checks the bunker's account. Never run `zsp publish` from a laptop with a personal key. If a release is ever published under the wrong key, delete those events (NIP-09) and republish from the right one.

==== APK signing key continuity

Every asset event records the APK's signing certificate hash. For the EAS production keystore that is `9106c54b976ba48e5e89de6fdf950059e1b2abee58851dcdb86d79e83ee5d56d` (`zsp utils extract-apk` prints it as `cert_fingerprint`). Android refuses to update an installed app from an APK signed by a different key, so a certificate change strands every Zapstore user. Therefore:

* Zapstore only ever gets the APK that `release.yml` builds on EAS with the production keystore. Never attach a locally built or locally signed APK to a Release.
* Never reset or replace the Android keystore in `eas credentials`.
* Optional follow-up: link the certificate to the Lightning Piggy account (NIP-C1 identity proof, kind `30509`) with `zsp identity --link-key`. This needs the EAS keystore and the account's signature. CI runs zsp in `--quiet` mode, which skips the linking prompt.

printf '%s' "$zapstore_bunker_uri" | gh secret set ZAPSTORE_BUNKER_URI --repo LightningPiggy/lightning-piggy-mobile
unset zapstore_bunker_uri
----

Never put the Lightning Piggy account's nsec in a secret. If a new bunker URI is ever needed, replace only `ZAPSTORE_BUNKER_URI`. Change `ZAPSTORE_CLIENT_KEY` only if it leaks, then create a fresh bunker connection too.

*3. First publish: v1.5.2, by hand.* The tag's Release must have `lightning-piggy-v1.5.2.apk` attached. If the Release run stopped before attaching it, re-run its failed jobs from the Actions page (`gh run rerun <run-id> --failed`). A re-run keeps the release event; *Run workflow* on Release doesn't attach assets. Then, with Richard's phone at hand:

[source,bash]
----
gh workflow run release-zapstore.yml --repo LightningPiggy/lightning-piggy-mobile --ref main -f tag=v1.5.2
----

Richard approves the new client's connection when the pre-flight step asks. If Amber prompts for the four kinds, approve them with "remember". If the publish step then fails on a Blossom signature timeout, re-run it: the remembered permissions now apply. When it finishes, check https://zapstore.dev/apps/com.lightningpiggy.app shows the Lightning Piggy account as publisher.

*4. From the next release on* it runs automatically after *Release*. The bunker connection signs without prompts.

==== Limits

* zsp only looks at the 10 most recent GitHub Releases, so a manual run can't publish an older tag.
* The universal APK (~300 MB) is uploaded to Blossom on every release. Per-ABI APKs would shrink downloads (separate change).
* To upgrade zsp, bump `ZSP_VERSION` and `ZSP_SHA256` together (`gh api repos/zapstore/zsp/releases/tags/vX.Y.Z --jq '.assets[] | .name + " " + .digest'`). Re-read the zsp README for schema changes (e.g. `zsp apk --extract` became `zsp utils extract-apk`), then repeat the dry run below.

==== Dry run (local, offline, never signs)

`--offline` makes no network calls. With an `npub` as `SIGN_WITH` it only prints *unsigned* events, which can't be published. It needs a local APK, and relative paths resolve against the config's folder, so build a copy of the config with absolute paths:

[source,bash]
----
gh release download v1.5.1 -p '*.apk' -D /tmp/zapstore-apk
zsp utils extract-apk /tmp/zapstore-apk/lightning-piggy-v1.5.1.apk   # package, version, cert_fingerprint
repo=$(git rev-parse --show-toplevel)
sed "s#: \./#: $repo/#; s#^  - \./#  - $repo/#" "$repo/zapstore.yaml" > /tmp/zapstore-offline.yaml
echo 'release_source: /tmp/zapstore-apk/lightning-piggy-v1.5.1.apk' >> /tmp/zapstore-offline.yaml
SIGN_WITH=npub1y2qcaseaspuwvjtyk4suswdhgselydc42ttlt0t2kzhnykne7s5swvaffq \
  zsp publish -q --offline /tmp/zapstore-offline.yaml > /tmp/zapstore-events.json
node --test scripts/zapstore-signer-preflight.test.mjs
----

`zsp publish --check zapstore.yaml` also works locally. It is read-only: it fetches and parses the latest Release's APK and contacts no relay or signer.

=== F-Droid

https://f-droid.org[F-Droid] is a catalogue of free and open-source Android apps. Publishing a React Native app to F-Droid requires additional steps because F-Droid builds apps from source and verifies all dependencies are FOSS.

==== Key Considerations

* F-Droid builds from source — the app must compile in their build environment
* React Native apps have two dependency systems (npm + Gradle), both of which F-Droid scans for non-free components
* The `android/` subdirectory must be specified via the `subdir` directive in the F-Droid metadata
* Some npm dependencies may include pre-built binaries that F-Droid flags — these need to be reviewed and whitelisted or replaced

==== Steps to Submit

1. Ensure the app builds reproducibly from source
2. Create a metadata file following the https://f-droid.org/docs/Build_Metadata_Reference/[F-Droid metadata format]
3. Submit a merge request to the https://gitlab.com/fdroid/fdroiddata[fdroiddata] repository on GitLab
4. F-Droid maintainers review the submission and verify the build

See the official guide: https://f-droid.org/2020/10/14/adding-react-native-app-to-f-droid.html[Adding React Native Apps to F-Droid]

=== Sideloading (Android / GrapheneOS)

Users on Android, GrapheneOS, or other custom ROMs can install specific versions directly from APK files.

==== From GitHub Releases

Attach APK builds to GitHub Releases so users can download and install specific versions:

[source,bash]
----
# Build an APK for sideloading
eas build --platform android --profile preview

# Download the APK from EAS
eas build:list --platform android --status finished
# Copy the build URL and download the APK

# Attach to a GitHub Release
gh release create v1.0.0 ./lightning-piggy.apk --title "v1.0.0" --notes "Release notes"
----

==== Installing on Device

Users can install the APK by:

1. **Direct download**: Download the `.apk` file from the GitHub Releases page on the device, then tap to install
2. **ADB install**: Connect via USB and run `adb install lightning-piggy.apk`
3. **Obtainium**: Users can add the GitHub repository to https://github.com/ImranR98/Obtainium[Obtainium], which automatically tracks releases and notifies users of updates
4. **Zapstore**: install and update from https://zapstore.dev/apps/com.lightningpiggy.app (every stable release is published there; see "Zapstore (Nostr App Store)")

On GrapheneOS, sideloading works the same as stock Android — enable "Install unknown apps" for the browser or file manager, then open the APK.

==== Version Management

Tag each release in Git and attach the corresponding APK to the GitHub Release. This gives users a clear history of versions to choose from:

[source,bash]
----
# Tag a release
git tag -a v1.0.0 -m "Release v1.0.0"
git push origin v1.0.0
----

=== System Appearance

`app.config.ts` uses `userInterfaceStyle: 'automatic'` and `expo-system-ui`
so the System theme follows OS appearance on Android and iOS. Changes to
this configuration or native dependency require a native rebuild; an OTA
JavaScript update alone is insufficient. `ThemeProvider` resolves the initial
appearance and subscribes to live changes; the global status bar uses the
resolved theme. Validate light/dark OS switching on rebuilt devices before merge.

=== Expo Config Plugins

The app uses custom Expo config plugins to modify native project settings during prebuild:

[cols="1,3", options="header"]
|===
| Plugin | Purpose

| `react-native-edge-to-edge`
| Swaps AppTheme's parent to `Theme.EdgeToEdge` and attaches the root `WindowInsetsCompat` listener. Required on Android 15+ — without it, the system stops dispatching the IME inset to RN (every keyboard API silently reads 0), and the conversation composer stays hidden under the docked keyboard (#194). Paired with `<KeyboardProvider>` + RNKC's `KeyboardStickyView` in `ConversationScreen.tsx`.

| `withAdjustResize`
| Sets `android:windowSoftInputMode="adjustResize"` in AndroidManifest.xml. Required for bottom sheets to slide up correctly when the keyboard opens. Retained alongside `react-native-edge-to-edge` because pre-Android-15 devices still use the classic resize path.

| `withAmberQueries`
| Adds the Amber signer package to the `<queries>` element in AndroidManifest.xml. Required on Android 11+ for the app to detect and communicate with Amber via NIP-55 intents.

| `expo-secure-store`
| Provides encrypted storage for sensitive credentials (NWC URLs, Nostr keys).

| `expo-image-picker`
| Camera and photo library access for profile picture selection. Permission message: "Allow Lightning Piggy to access your photos to set your profile picture."

| `expo-contacts`
| Device contacts access for finding friends. Permission message: "Allow Lightning Piggy to access your contacts to find friends."

|===

=== Deployment Checklist

Before releasing to production:

* [ ] TypeScript passes: `npx tsc --noEmit`
* [ ] ESLint passes: `npm run lint`
* [ ] Prettier passes: `npm run format:check`
* [ ] App tested on physical Android device
* [ ] App tested on physical iOS device (if applicable)
* [ ] **iOS provisioning profile is up-to-date with all *entitlement-bearing* capabilities declared in `app.config.ts`.** When you add a config-plugin that writes to the iOS entitlements file (NFC, push notifications, App Groups, Background Modes, etc.), the existing AppStore profile won't automatically include the new entitlement → Xcode signing fails the cloud build with `Provisioning profile … doesn't include the X capability`. *Permission-string-only* plugins (`expo-image-picker`, `expo-contacts`, `expo-location`) just add Info.plist usage strings — they don't trigger this and don't need a profile refresh. Hit by `v1.0.0-rc2` and `v1.0.1-rc1` over NFC. Recovery: enable the capability on the Identifier in https://developer.apple.com/account/resources/identifiers, regenerate the AppStore profile in Profiles, refresh EAS via `eas credentials --platform ios`. Full procedure in `docs/TROUBLESHOOTING.adoc` → "Release workflow fails on iOS with Provisioning profile … doesn't include the … capability".
* [ ] New git tag chosen (`vX.Y.Z` or `vX.Y.Z-rcN`) — the release workflow writes it into `app.config.ts`; do NOT hand-edit the file
* [ ] E2E tests pass: `maestro test .maestro/`
* [ ] Git tag created for release version
