== Security

This section documents how Lightning Piggy handles sensitive data, credential storage, and security boundaries.

=== Credential Storage

The app uses two storage mechanisms with different security levels:

==== SecureStore (Encrypted)

`expo-secure-store` provides encrypted storage backed by the iOS Keychain and Android EncryptedSharedPreferences. All sensitive credentials are stored here.

[cols="2,3,1", options="header"]
|===
| Key | Contents | Source

| `nwc_url_{walletId}`
| NWC connection URL containing the wallet's relay, secret, and pubkey. One entry per wallet.
| `walletStorageService.ts`

| `nostr_nsec`
| Nostr private key (nsec) for users who sign in with a private key directly.
| `NostrContext.tsx`

| `nostr_pubkey`
| Nostr public key. Stored for both nsec and Amber sign-in methods.
| `NostrContext.tsx`

| `nostr_signer_type`
| Either `"nsec"` or `"amber"` — indicates which signing method is active.
| `NostrContext.tsx`

|===

**Legacy key:** `nwc_connection_url` was used in the single-wallet version. The migration in `walletStorageService.ts` moves this to the `nwc_url_{id}` format and deletes the legacy key.

==== AsyncStorage (Unencrypted)

`@react-native-async-storage/async-storage` stores mostly non-sensitive data — the keys below contain pubkeys, settings, and public profile metadata. Decrypted *1:1 DM* plaintext no longer lives here: as of #848/#850 it persists exclusively in the SQLCipher-encrypted local DB (see <<Message Content at Rest (Threat Model)>>). The remaining known exception is decrypted *group-chat* plaintext (`group_messages_<groupId>`, `nostr_group_activity_<pubkey>`) — see the residual-risk note in that section.

[cols="2,3", options="header"]
|===
| Key | Contents

| `wallet_list`
| JSON array of wallet metadata (id, alias, theme, order, lightning address). No secrets.

| `onboarding_complete`
| Boolean flag — `"true"` after the user completes onboarding.

| `user_display_name`
| The user's chosen display name.

| `user_fiat_currency`
| Selected fiat currency code for balance display.

| `lightning_address`
| The user's lightning address for receiving payments.

| `nostr_contacts_{pubkey}`
| Cached Nostr contact list with 24-hour TTL. Contains only public data (pubkeys, profile metadata).

|===

NOTE: The app still stores **decrypted group-message plaintext** in AsyncStorage to power `GroupConversationScreen` and the group previews on the Messages tab (`group_messages_<groupId>`, `nostr_group_activity_<pubkey>`). This is the known at-rest residual — 1:1 DM plaintext moved to the encrypted DB in #848/#850. See <<Message Content at Rest (Threat Model)>> below.

=== NWC URL Security

NWC (Nostr Wallet Connect) URLs contain the wallet's secret key and relay information. The app handles these carefully:

* **Storage**: NWC URLs are always stored in SecureStore, never AsyncStorage.
* **Validation**: `nwcService.validateNwcUrl()` checks URL format, required parameters (`secret`, `relay`), and relay URL validity before saving.
* **Display**: NWC URLs are never displayed in full in the UI.
* **Deletion**: When a wallet is removed, its NWC URL is explicitly deleted from SecureStore via `deleteNwcUrl()`.

=== Nostr Key Management

==== nsec (Direct Private Key)

When a user signs in with an nsec:

1. The nsec is decoded and validated via `nostr-tools/nip19`
2. The private key is stored in SecureStore (`nostr_nsec`)
3. All event signing is done locally using `nostr-tools/pure.finalizeEvent()`
4. The nsec never leaves the device

==== Amber Signer (Android)

When a user signs in with Amber:

1. Only the public key is stored in the app (in SecureStore as `nostr_pubkey`)
2. The private key remains exclusively in the Amber app
3. Event signing is delegated to Amber via NIP-55 intents
4. Each signing request requires explicit user approval in Amber

The Amber approach provides stronger key isolation — the private key never enters Lightning Piggy's process space.

=== Account Creation

New Nostr identities are generated locally:

1. `nostr-tools/pure.generateSecretKey()` creates a cryptographically random keypair
2. The nsec is stored in SecureStore
3. A safety tip is displayed: "You don't need to use your real name or photo for your profile"
4. The user is shown their nsec with a copy button and backup warning

=== Logout and Cleanup

On logout, all Nostr credentials are explicitly deleted from SecureStore:

[source,typescript]
----
await SecureStore.deleteItemAsync('nostr_nsec');
await SecureStore.deleteItemAsync('nostr_pubkey');
await SecureStore.deleteItemAsync('nostr_signer_type');
----

Cached contact data in AsyncStorage is also cleared.

=== Input Validation

[cols="1,3", options="header"]
|===
| Input | Validation

| NWC URL
| URL format check, required `secret` and `relay` parameters, relay URL scheme validation (`wss://`)

| nsec
| Bech32 decoding via `nostr-tools/nip19.decode()`, must produce a valid private key

| npub
| Bech32 decoding, must produce a valid 32-byte public key

| Lightning address
| Must contain `@` and resolve via LNURL-pay (LUD-16)

| Payment amounts
| Validated against LNURL-pay `minSendable` / `maxSendable` bounds

|===

=== Network Security

* All relay connections use `wss://` (WebSocket Secure)
* Image uploads to nostr.build use HTTPS
* LNURL-pay callbacks use HTTPS

=== Message Content at Rest (Threat Model)

This section documents where decrypted Nostr message content lives on disk and what an adversary with the device can recover. It supersedes the original "document + accept" analysis (#192): the plaintext-in-AsyncStorage design it described was retired in #848/#850 in favour of app-level encryption at rest (the option-4 outcome that analysis recommended, delivered as a SQLCipher store rather than per-blob AES). The design threat model is a **seized device** — e.g. border control taking the phone for forensic imaging.

==== Where message content lives now

[cols="3,3,2", options="header"]
|===
| Data | Where | At-rest protection

| 1:1 DM plaintext (NIP-17 rumors + legacy NIP-04), incl. delivery ticks, rumor ids and optimistic unsent rows
| `dm_messages` table in `lightningpiggy.db` (op-sqlite + SQLCipher)
| **Whole-file SQLCipher encryption**; 256-bit key held only in the OS keystore (`expo-secure-store`, `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`, excluded from backups). Every open asserts `PRAGMA cipher_version` and refuses a plaintext fallback.

| Legacy plaintext DM caches (`amber_nip17_cache_v1*`, `nsec_nip17_cache_v1*` files; `nostr_dm_inbox_v1_*`, `nostr_dm_conv_v1_*` AsyncStorage blobs)
| **Retired.** One-time migrations (#848 `dmStoreMigrationRunner`, #850 `dmBlobMigration`) import each cache into the encrypted DB, then delete it with verification (populate → delete → verify → flag; the flag is never set while plaintext survives). Pre-#288 unsuffixed remnants are deleted too.
| n/a after migration — nothing writes these keys any more

| Marmot (MLS) 1:1 plaintext
| `dm_messages` rows with `protocol = 'marmot'`, same table as above
| Same SQLCipher protection as other 1:1 DMs.

| Marmot (MLS) state — group secrets, key-package private keys, each group's decrypted message history, photo file keys, MIP-05 push records
| `marmot_kv` table in `lightningpiggy.db`, keyed by owner (see `DATA_STORAGE.adoc` → "Marmot (MLS) state")
| Same SQLCipher protection. Deleted per account on sign-out (`deleteMarmotStateForOwner`).

| Group-chat plaintext (`group_messages_<groupId>`, `nostr_group_activity_<pubkey>`), NIP-17 *and* Marmot groups
| AsyncStorage (unencrypted)
| **Known residual.** App sandbox + OS file-based encryption only. Wiped on logout/account-wipe (#944); moving it into the encrypted store is the tracked follow-up. A Marmot group photo's row embeds its file keys (`#lpe=1` URL), so the residual covers those photos too.

| Last-seen cursors (`*_last_seen_*`)
| AsyncStorage
| Bare unix timestamps — no content.
|===

==== Threat model: seized device (border control)

What the design protects:

* **Forensic imaging of the flash (device off or locked).** The DM store is SQLCipher ciphertext — content *and* metadata. The DB key is wrapped by the hardware keystore and is not present in any file an imaging tool can lift; it is also excluded from cloud/device-migration backups, so a backup-restore of the app data yields an unopenable ciphertext file (the app detects this and re-syncs from relays rather than shipping a key in the backup).
* **Casual physical access / other apps.** Unchanged from before: app sandbox, no export UI.
* **Cross-account leak on a shared install.** Logout wipes the signed-out owner's DB rows, every legacy cache key (suffixed *and* unsuffixed), the group-chat blobs, and — on last-identity logout — deletes the DB file *and* its keystore key (`wipeLocalDmStore`). A lone key or a lone ciphertext file is never left behind.

What it cannot protect against (out of scope at the app layer):

* **Compelled or observed device unlock.** After first unlock the keystore will serve the DB key to the app; an adversary who can compel the passcode (or seize the phone unlocked and keep it powered) operates as the user. Raising this bar needs an *app-level* lock that gates the DB-key read behind a separate credential/biometric, plus optionally a panic-wipe — tracked as follow-ups, deliberately not bundled into the storage migration.
* **Rooted device with the app running.** Decrypted rows transit RAM while rendered.
* **Group-chat residual.** Until group messages get the same treatment, `group_messages_*` is readable from an unlocked seized device.
* **Relay-side copies.** At-rest encryption protects the device only; NIP-17 wraps remain on relays and are re-fetchable by anyone holding the nsec. Marmot kind-445 events also stay on relays, but the nsec alone can't decrypt them — that needs the MLS group state in `marmot_kv` (and MLS forward secrecy means even that can't read epochs it has already deleted).

==== What servers see: Marmot messaging

* **Nostr relays** see kind-445 group events signed by per-message ephemeral keys and tagged with the group's Nostr id (`h`), so they can link events of one group but not see members, content or the sender. Key packages (kind 30443) are public and signed by the account. Welcomes and push triggers are NIP-59 gift wraps, which show only the recipient.
* **Blossom servers** store photo ciphertext and its hash. The key is derived from the group's MLS epoch secret and never leaves the group; uploads are `application/octet-stream`, and when the user's servers refuse that they go to the fallback servers in `ENCRYPTED_BLOB_FALLBACK_SERVERS`.
* **Notification servers (MIP-05)** — e.g. White Noise's Transponder for White Noise users — receive kind-446 triggers we gift-wrap after a message: they decrypt the device tokens inside and learn *that* those devices should be woken, and when. They never see the message, the group or the sender. We never see anyone's device token; we only hold the encrypted ones members gossip in the group.
* **Apple / Google (APNs / FCM)** deliver a content-free push, so they see push timing to a device only. Lightning Piggy registers for Marmot pushes only when the user opts in (Settings → Security; off by default, per account): the app then asks Apple/Google for a native token, which Firebase/APNs see like any app's. FCM auto-init is off until that opt-in, and the Android manifest also sets `firebase_analytics_collection_deactivated=true` and `google_analytics_adid_collection_enabled=false` (`plugins/withFcmAutoInitDisabled.js`), so no Firebase Analytics or advertising-id collection ever runs.
* **Our notification servers (MIP-05 Transponder, one per app id)** — when push is on, each of our groups holds this device's token sealed to our server (ChaCha20-Poly1305 under an ECDH key only the server can derive, sealed afresh per group). The spec-required token fingerprint is the same in every group, so someone who is in two of our groups can tell both records belong to one device — and two accounts on one phone that both publish it would be linkable the same way. The opt-in is therefore **per account** (`marmot_push_enabled_v1_<pubkey>`): an account added or switched to never inherits it, and enabling it while another account on the phone has it on shows a one-line warning. The server learns, per trigger, that a device should be woken and when — so how many devices one message fans out to, and how often this phone is woken; triggers arrive gift-wrapped from fresh ephemeral keys, so it doesn't learn who sent them, which group or who you talk to, and it never sees content. A group member (or ex-member) who kept a sealed token can keep waking the device (MIP-05 "Best-effort revocation"); turning push off or removing the account therefore deletes the token at Apple/Google once no other account on the phone uses push (retried at the next start if it fails, and no account can turn push on until it succeeds). While another account still uses the token, the signed kind-449 removals are the retraction — unless the signer declined or the pass didn't finish, in which case the token is replaced so leftover records can't link the accounts. On Android that kills every copy; iOS may hand the same APNs token back on re-registration, so there it is best-effort — the worst case is a content-free "New message" alert. Owner proofs returned by Amber / NIP-46 are checked against the exact requested event and verified before use.

==== Rules for new code

* Decrypted DM/group content, or anything derived from it (previews, search indexes), goes in the encrypted DB — **never** AsyncStorage or a plain file.
* Keys/credentials go in `expo-secure-store`; bulk data never does (Keychain items must stay small).
* Any migration off a plaintext store must follow the `dmStoreMigration` ordering: populate the encrypted copy, delete the plaintext, **verify** it is gone, only then set the migrated flag.
* Every wipe path (logout, account removal) must cover new keys — add them to `wipeAccountCaches` / `wipeDmStoresForAccount` in the same PR that introduces them.
