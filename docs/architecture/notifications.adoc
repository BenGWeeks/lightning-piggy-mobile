= OS Notifications Architecture
:toc:
:source-highlighter: rouge

This document explains how Lightning Piggy delivers OS-level
notifications (incoming DMs, group messages, payments, zaps) to a
backgrounded or closed app *without* depending on Firebase Cloud
Messaging or any other Google Play Services component. The exceptions
default on for the first account on a phone (subject to OS permission), with
additional accounts opting in: Marmot push (MIP-05), a content-free
"New message" wake through Apple/Google — see "Marmot messages and
MIP-05 push" below — and, under the same push switch, the notification
watcher's per-category alerts for DMs, zaps, mentions and NWC wallet
activity — see "The notification watcher" below.

It is the canonical reference for the foundation landed in PR for
issue https://github.com/LightningPiggy/lightning-piggy-mobile/issues/279[#279].

== Current implementation note

The foundation description below predates the Android foreground service
(merged in #958). That service now hosts the opt-in background message watch
and periodic NWC incoming-payment checks. See
link:../BACKGROUND_PAYMENTS.adoc[Android background payments] for current scope,
setup, delivery limits and device validation. Payment checks cover Android NWC
wallets; the foundation background worker itself only checks messages and cache
activity. Its iOS scheduling estimates below are not a guaranteed delivery bound.

== Why local-first (working without Google Play Services)

Lightning Piggy targets users on de-Googled Android distributions
(GrapheneOS, CalyxOS, /e/OS, microG-flashed stock ROMs). FCM
requires Google Play Services to be present on the device — when GMS
is absent, an FCM-based notification stack silently never fires, and
the affected user has no way to fix it short of reflashing.

Standard React Native push libraries (`react-native-firebase/messaging`,
`@notifee/react-native` with FCM transport, OneSignal, etc.) all sit
on top of FCM and inherit this constraint. They are excluded from
Lightning Piggy's dependency graph by policy, not just preference.
(`expo-notifications` itself links the Firebase Messaging SDK on Android;
it stays dormant — auto-init disabled by `plugins/withFcmAutoInitDisabled.js`
— until Marmot push is enabled, and nothing else depends on it.)

Apple Push Notification service (APNs) is the equivalent on iOS but
requires us to operate a remote push server that holds an APNs token
per device and forwards events to it. We deliberately do not run a
backend (the app talks to relays + LNbits + Boltz directly), so APNs
is out for the same architectural reason that FCM is out: there is
no remote sender. iOS notifications therefore arrive via local
notifications fired by the JS runtime when it next runs (see
"iOS background story" below).

Marmot changed one part of this: MIP-05 defines a remote sender that
learns nothing about the message — a notification server that only turns
an encrypted device token into a content-free native push. Lightning Piggy
runs one per app (a MIP-05 Transponder) and offers it for
Marmot chats. Everything above still holds when it is off,
and on a de-Googled Android it simply can't be turned on.

== The three pieces

[cols="1,3"]
|===
| Component | Role

| `src/services/notificationService.ts`
| Single integration point. Exposes typed `fireNotification(payload)`
to every trigger site (DM rumor decrypt, payment settle, zap receipt).
Owns Android channels, the foreground permission flow, and the
lock-screen content privacy preference. Backed by `expo-notifications`
LOCAL notifications (no FCM token requested unless the user opts into
Marmot push).

| `expo-background-task` + `src/services/backgroundSyncService.ts`
| The cross-platform background worker — WorkManager on Android,
BGTaskScheduler on iOS — registered in `src/services/backgroundTask.ts`.
When the UI isn't mounted the OS periodically runs `runBackgroundSync`,
which does DETECT-AND-PING: it notices new encrypted inbound traffic
and fires a generic "new message" notification *without decrypting*.
No custom native code; the config plugin wires the platform bits.

| Android foreground service (opt-in, #958)
| `modules/background-dm-service`: a Kotlin `Service` that starts the JS
runtime and runs the headless message watch (plus NWC incoming-payment
checks) for near-realtime delivery, with a `BootReceiver`. The module
manifest declares the service and receiver; `plugins/withForegroundService.js`
adds permissions. Off by default (Settings → Notifications); periodic
`expo-background-task` registration is independent and subject to OS scheduling
and background-execution restrictions. The service holds no permanent wake
lock, so deep Doze can delay delivery until maintenance windows.
|===

== Android background story

----
[ WorkManager ] ──(~15 min)──> runBackgroundSync()
                                   │
                                   ├── queries relays for new kind-1059
                                   │   gift wraps + kind-4 DMs addressed
                                   │   to us (DOES NOT decrypt)
                                   │
                                   └─> notificationService.fireMessageNotification({...})
                                          │  (generic "New message" copy)
                                          └─> expo-notifications local schedule
                                                 │
                                                 └─> OS notification shade
----

* The background worker is scheduled by `expo-background-task`
  (WorkManager under the hood). ~15-minute floor — Android won't run a
  periodic task more often. That cadence suits detect-and-ping: we only
  need to notice new traffic arrived, not stream it.
* DETECT-AND-PING, never decrypt in the background. This works for BOTH
  nsec and Amber users (Amber can't decrypt headlessly), and keeps
  plaintext off-screen. See `backgroundSyncService.ts`.
* `POST_NOTIFICATIONS` runtime permission is requested from the
  FOREGROUND at app launch — not lazily from a fire path, since a
  headless task can't present the OS dialog. See
  `notificationService.requestNotificationPermission()`; fire paths
  only ever call `hasNotificationPermission()`.
* The opt-in foreground service (`background-dm-service`, #958) keeps a
  relay socket alive for near-realtime delivery; its manifest permissions
  (`FOREGROUND_SERVICE`, `RECEIVE_BOOT_COMPLETED`, …) come from
  `withForegroundService.js`. See `BACKGROUND_PAYMENTS.adoc`.

This path works on stock Android, GrapheneOS, microG, and any other
AOSP derivative. It does not work in scenarios where the user has
manually battery-restricted the app — that's a documentation
problem, addressed in onboarding.

== iOS background story

iOS has no equivalent to Android's foreground service. The two
alternatives we evaluated:

1. **Silent push via APNs** — requires us to run a remote server
   that holds APNs tokens and forwards events. *Rejected* as the general
   mechanism — same architectural reason as FCM (no backend). For Marmot
   chats only, MIP-05 push (below) is the exception: our
   notification server sends a generic alert, never message content.
2. **`audio` background mode keep-alive trick** — plays a near-silent
   audio stream so iOS keeps the app process alive. App Store
   review reliably rejects this. *Rejected.*
3. **`BGTaskScheduler` periodic refresh** — OS-controlled cadence,
   typically 15-30 min between executions, may be longer if the
   device is locked / on battery / hasn't been used recently.
   *Accepted as the iOS reality.*

Trade-off the user must understand: on iOS, message and payment
notifications can be delayed by up to ~30 min, and the device must
have been used recently for the OS to schedule the task at all.
This will be explained in iOS onboarding when the iOS build ships.

== Privacy: lock-screen content

Decrypted DM plaintext is *never* written to the notification body by
default. The user must explicitly opt in via the Settings toggle on
SecurityScreen (preference key `notif_pref_lockscreen_content_v1`).

How it's enforced:

* **Per-notification level (the real guard)** — when the preference is
  OFF (default), `notificationService.fireNotification` substitutes the
  caller-provided title/body with a generic
  `"New message" / "Open Lightning Piggy to read"` pair before
  scheduling. The actual content never enters the OS notification store
  at all, even briefly. This is what makes the opt-in toggle meaningful.
* **Android channel level** — both `messages` and `payments` channels
  use `lockscreenVisibility: AndroidNotificationVisibility.PRIVATE`
  (not `SECRET`). PRIVATE lets the notification appear on the lock
  screen while honouring the user's system-level "hide sensitive
  content" setting. We deliberately avoid `SECRET`: it would hide the
  entry entirely even after the user opts into lock-screen content,
  making the toggle a no-op on Android.

Only routing metadata rides in the notification's `data` field — the
`kind` plus conversation/group/wallet ids — *not* the plaintext title
or body. The in-app screen we navigate to on tap reloads the real
content from the local store once the user has unlocked.

== Per-channel mute

Android 8+ surfaces every channel separately in system Settings →
Apps → Lightning Piggy → Notifications. A user who wants payment
alerts but no message alerts (or vice versa) can mute either channel
without affecting the other or uninstalling the app.

In-app per-channel toggles are a follow-up — for the foundation PR,
the system Settings UI is the only mute path.

== The notification-manager service as single integration point

Every trigger site in the app — `NostrContext.tryRouteGroupRumor`,
the future DM-inbox notification fire, payment-settled handlers,
zap-received handlers — calls `fireNotification(payload)` and
nothing else. They never reach into `expo-notifications` directly.

This seam exists so we can:

* swap the backing notification library without touching trigger
  sites,
* add notification grouping / collapsing in one place (multiple
  DMs from the same sender → one notification),
* implement quiet hours / per-contact mute / snooze in one place,
* add badge counts in one place,

— all without an audit pass through every trigger site.

== Marmot messages and MIP-05 push

Marmot (MLS) messages raise the same local notifications as NIP-17 ones
while the app is running and its Marmot session is up
(`useMarmotDmInbound` / `useMarmotGroups` → `fireMessageNotification`). The
background detect-and-ping worker and the Android background message watch
subscribe to gift wraps (kind 1059), not to kind-445 group events, so without
push a Marmot message that arrives while the app is closed raises no alert.

*Send side.* When we message a group, `marmotPushNotifier.ts` gift-wraps the
other members' encrypted device tokens to their notification server, which
wakes their phones (White Noise users via White Noise's Transponder, Lightning
Piggy users via ours).

*Receive side (default on for the first account).* Settings → Notifications →
"Instant alerts". First account means no other account on this phone has push
enabled or a stored notification preference, including an explicit OFF.
`notificationDefaults.ts` resolves missing preferences after legacy migration;
`useNotificationDefaults` runs once Wallets is visible after sign-in. It requests
the existing OS permission flow, then uses the existing enable path to obtain the
token and schedule per-group records. Local signers publish automatically;
Amber / NIP-46 approvals wait for the existing "Finish setup" and watcher Retry
surfaces, with no automatic signer batch at launch.

The phone has one token: accounts publishing it show the same fingerprint in
chats, making two accounts on one phone linkable to anyone chatting with both.
Additional accounts therefore remain opt-in, with the existing linkability
warning. The per-account switch is `marmot_push_enabled_v1_<pubkey>`.
`notification_preference_explicit_v1_<pubkey>` records an explicit choice (`1`)
or an already-applied default (`0`); either prevents reconsidering that default.
Legacy stored `0` / `1` preferences are respected, including the old device-wide
switch migrated to the active account. Existing enabled installs keep their
Instant alerts preference; an explicitly disabled switch stays off.

The automatic setup is one cancellable task bound to one account
(`notificationDefaultsTask.ts`). It spans the OS permission prompt, the token
fetch and several storage writes, so every write — and the push runtime commit
inside `enableMarmotPush` (token, wake task, group records) — goes through one
guard, checked immediately before and after each step against the *live*
identity at call time, never a render-time snapshot (tabs are `freezeOnBlur`).
The guard fails once the account changes (switch or sign-out bump the task
generation), once account cleanup aborts the task (the wipe drains any write
already handed to storage, then deletes the keys; nothing is recreated), or
once the user makes a notification choice of their own (`enableMarmotPush`,
`disableMarmotPush` and `setWatcherCategory` record a manual change before
anything is awaited): the user's choice stands and the task writes nothing more.
A stale task discards the device token and rolls back its own opt-in write.
Wallets losing focus does not cancel a task that has started.

The order is: OS permission (asked for undetermined permission whether or not
anything else runs), push enablement, watcher categories, automatic push OFF,
and the decision marker LAST — so a crash, a cancelled token fetch or a failed
write leaves the missing preferences absent and the next launch retries them.
Denial leaves both Instant alerts and More alerts off alongside the existing
phone-settings banner and setup retryable. Permission can be restored through
the existing settings surface. A saved ON preference keeps showing on while the
OS blocks alerts (the banner says why none arrive), so the user can still turn
it off and retract the registrations; only the status row and the category
switches wait for permission.

. `marmotPushRegistration.ts` asks Apple/Google for this device's *native*
  token (`getDevicePushTokenAsync` — FCM on Android, APNs on iOS; never Expo's
  push service) and picks the notification server by app id:
+
[cols="2,3,2"]
|===
| App id | Server (Transponder) | Notes

| `com.lightningpiggy.app` | `npub1v5lrt4u7vhfnmxwk6c3uepcsrvs4jqyy3z3jrfm5kw73yp0wv2ts5pnwjs` | APNs topic = production bundle id
| `com.lightningpiggy.app.preview` | `npub1rzy2h0rhqmn44tqepvy4h93082878cackvked5lp3wghzkwe3rmsetjeya` | APNs topic = preview bundle id
| `com.lightningpiggy.app.dev` | `npub15vns5zhkr3vq95rg330gmtea6mz2xs24um0hey396nd06p8kfl9say2equ` (overridable at bundle time with `EXPO_PUBLIC_MARMOT_PUSH_DEV_SERVER`) | APNs *sandbox* environment, topic = dev bundle id; FCM too. The APNs environment follows the build's signing, not the bundle id: the iOS Simulator and `expo run:ios` dev clients get sandbox tokens (served), but an EAS-built `.dev` app on a physical iPhone gets production tokens, which no server serves for the `.dev` topic
|===
+
An "Advanced" field accepts another server's npub (it must hold Lightning
Piggy's APNs/FCM credentials to deliver); its relay hint is the first relay of
its kind-10050 list. The built-in servers carry *no* relay hint: White Noise
(MDK) sends a trigger only to the record's hint when it has one, so a hint pins
it to that relay until each member re-signs (the old fixed `wss://nos.lol` hint
stranded every trigger, because our self-hosted servers can't reach nos.lol from
their IP); our own notifier sends to the hints *and* the server's
10050. Without one,
senders look up the server's kind-10050 — currently `relay.eu.whitenoise.chat`,
`relay.ditto.pub`, `relay.coinos.io` and `relay.primal.net`, which the servers
also subscribe to — so moving the servers to other relays (e.g. one Lightning
Piggy hosts) is a server-side change with nothing to re-sign. Records published
with the old hint are re-signed once, without it (one signer prompt per group
for Amber / NIP-46, at the next send or "Finish setup").
. `marmotPushToken.ts` seals the token to the server (MIP-05 "Token
  encryption"); `marmotPushRegistrar.ts` publishes it in every Marmot group as
  a kind-447 self-update with an owner proof — see `SOLUTION_DESIGN.adoc` →
  "Marmot (MLS) messaging" for the protocol and signer details.
. Other members' clients now trigger our server, which sends a content-free
  push:
** *iOS* — the server sends a generic APNs alert ("Lightning Piggy" / "New
   message"), shown by the OS.
** *Android* — FCM delivers a data-only message (Transponder has no FCM alert
   mode). `marmotPushWake.ts` (defined from `index.ts`, so it also runs
   headless after the app was swiped away) posts the generic "New message"
   ping itself — unless the app (foreground or a running session in the
   background) showed a Marmot message in the 15 s before the push (the sender publishes
   the message first) or the 6 s after it. If the real message turns up
   later, showing it clears the generic ping.
. Tapping the generic alert opens the Messages list (no thread id), and
  focusing that list clears it (#1142). A burst of pushes replaces one
  generic alert instead of stacking.

*No double alerts.* A remote push that arrives while the app is open is
hidden by the `setNotificationHandler` in `notificationService.ts`
(`isRemotePush`) — but only once the app has *shown* a Marmot message (an
alert, or the message landing in the open thread) within the last 15 s,
waiting up to 2 s for it. Being in the foreground alone proves nothing: the
push may be for another signed-in account, or arrive before the session has
the message. (That applies to iOS's server alert; Android's data-only push
is never shown itself — the wake task, which applies the same evidence rule,
owns its generic alert.)
When the app shows a Marmot message itself, it clears any generic push
alert already in the tray (ours on Android, the server's data-less one on
iOS); opening the Messages list clears them too.

*Turning it off* sends a signed kind-449 removal into each of that account's
groups, then — once no account on the phone still uses push — deletes the
token at Apple/Google (`unregisterForNotificationsAsync`; retried at the next
start if offline), so copies the members already hold stop working. While
another account still uses it, the token is kept only if every group took
the signed removal; if the signer declined or the pass didn't finish, the
token is replaced (deleted, and a new one fetched for the accounts still on
push) so the leftover records can't link the two accounts. Enabling push
never hands out a token whose deletion is still owed. *Removing an
account* that had push on can't sign removals (its key is gone), so it
deletes the token instead and fetches a fresh one only if another account
opted in. iOS may return the same APNs token after re-registering, so
revocation there is best-effort.

*Known residuals.* A push carries no message id (by design — the server
must learn nothing), so de-duplication is a heuristic: on Android a recent
Marmot alert for an *earlier* message can stand in for this push's generic
one (the look-back is kept short), and on iOS an app that is still running
for a few seconds after being backgrounded can show both its own alert and
the server's. Exact matching would need a message correlation the protocol
doesn't carry (and an iOS notification service extension).

*Privacy* (behind "Privacy details" next to the switch): Apple/Google learn
that the phone got a notification and when, not what it says. Our server gets
device tokens sealed so only it can open them, and opens them only to deliver
each push: it receives gift-wrapped triggers from fresh ephemeral keys and
decrypts the device tokens in each, so it can see how many
phones one message fans out to and how often this phone is woken, but not who
sent it, which chat it was, or who you are. People in your Marmot chats can
see that this phone has push on, and the same phone shows the same token
fingerprint in every chat — hence the additional-account opt-in above.

*Limits.* On de-Googled Android there is no FCM token, so enabling reports
"unavailable" and the local paths above remain the only ones. A force-stopped
Android app receives no FCM messages until it is opened again (an Android
rule). Pushes are best-effort (MIP-05): a missed push never affects message
delivery.

== The notification watcher (DMs, zaps, mentions, payments)

MIP-05 only covers Marmot groups, where the *sender* triggers the push. For
everything else there is no sender-side mechanism, so Lightning Piggy runs a
small open-source *watcher*
(https://github.com/BenGWeeks/lightning-piggy-watcher[lightning-piggy-watcher],
npub `npub17hcchazg4akxq4ccuskxmxegl2euyz8je7h6xjthekeyz8pux78qfzgph2`) that
watches relays for events addressed to registered users and sends the same
kind of content-free push. Its `PROTOCOL.md` is the wire contract; the app side
is:

[cols="2,5"]
|===
| Module | Role

| `watcherRegistration.ts` | Pure wire format: the kind-8480 rumor, the NIP-59 wrap (seal signed by the user's signer), NWC proofs, relay selection, fingerprints. Checked against a vendored copy of the watcher's own parser (`watcherRegistrationConformance.test.ts`).
| `watcherPushRegistrar.ts` | Lifecycle: when to (re)register / unregister, debounce, `ts` monotonicity, status.
| `watcherPushStore.ts` | Per-account state in AsyncStorage (`watcher_push_v1_<pubkey>`): categories, last `ts`, what was last registered (a hash of the token, never the token itself).
| `watcherPushTransport.ts` | Publishes the wrap to the watcher's kind-10050 relays (damus is skipped while others are listed: it requires NIP-42 AUTH and rate-limits).
| `watcherPush.ts` / `WatcherPushBridge.tsx` | Wiring: the token from `marmotPushRegistration.ts` (shared — one native token per phone), the signer (`createMarmotSigner`), the account's relays and NWC wallets.
| `watcherPushReceive.ts` | Recognising a watcher push on each platform, foreground policy, tap routing.
|===

*Settings.* Under the push switch (Settings → Security → Push notifications),
"More push notifications" lists four toggles — Messages (NIP-04/17), Zaps,
Mentions, Payments — each defaults on for the first account and is only
switchable while *this
account's* push is on (they need the device token the push switch obtains).
Like the Marmot switch, everything is per account: the registrar only gets the
token for an account that turned push on itself (`currentPushDevice(pubkey)`),
so additional accounts do not automatically register with the watcher. Stored
categories (including legacy OFF) are preserved. `explicitlySet` in the watcher
state records category changes; automatic defaults set it to false so a remote
signer's first registration waits for Retry / Finish setup. The privacy note
there says what the watcher learns.

*What a registration contains.* `{v:1, action, app, platform, token,
apns_env?, categories, relays, nwc, ts}` — `app` is the build's application id
(`.dev` / `.preview` / production, all accepted by the watcher; also the APNs
topic), `apns_env` comes from `getIosPushNotificationServiceEnvironmentAsync`
(`development` → `sandbox`). `relays` (≤8, public `wss://` hostnames only,
normalised the way the watcher does) are, in priority order: the NWC wallet
relays (only if Payments is on — NWC notifications are only published there),
the user's DM inbox (kind 10050, if Messages is on), then their read relays
(kind 10002). The watcher's own relays (`WATCHER_DEFAULT_RELAYS`: primal,
ditto.pub, coinos.io, relay.eu.whitenoise.chat — the watcher's `WATCHER_RELAYS`)
are left out: it always watches those. `nwc` holds up to 3 connections (the first NWC wallets
in display order), each with a BIP-340 proof signed by that connection's own
secret over `sha256("lightning-piggy-watcher/nwc/v1:<user>:<wallet>")`, so only
the holder of the connection secret can claim its notifications.

*When it registers — and when the signer is asked.* A registration is one seal
(one NIP-44 encryption + one signature by the user's key). For Amber / NIP-46
that is a prompt, so `planWatcherSync` decides:

[cols="3,2,2"]
|===
| Trigger | nsec | Amber / NIP-46

| Category toggle (debounced 2 s — a burst is one signature) | register | register
| All categories off | unregister | unregister
| Push switched off | unregister first (Settings; bounded at 20 s), then Marmot push deletes the token — or, if another account still uses push and the unregister didn't go through, replaces it | same — if declined, the token deletion still ends Android pushes
| Push token changed | register | register
| NWC wallet added / removed | register | register
| Relay-list change only | register (10 s settle) | folded into the next registration
| App start, registration < 7 days old | nothing | nothing
| App start, registration ≥ 7 days old | refresh | refresh (the only start-time prompt)
| App start, an earlier change never went through | register | *pending* — "Retry" in Settings
| Sign-out of the active account | unregister *before* the key is wiped (bounded at 20 s), then the token is deleted (Marmot push teardown) | same (one prompt; if declined or unanswered, the token deletion still ends Android pushes)
| Removing another signed-in account | its key isn't the active signer: the token deletion kills the registration on Android; iOS best-effort (APNs may reissue the token; the watcher deletes registrations not refreshed for 30 days) | same
|===

Everything runs on one serial chain, and every signer instance (Marmot
sessions included) shares one intent queue — Amber rejects concurrent intents.
A registration prepared for an account that signs out or switches meanwhile is
dropped before publishing; a sign-out unregister stays bound to the account it
was asked for (never a successor) and is abandoned if the sign-out stops
waiting for it.
`ts = max(now, lastTs + 1)` — if the clock went back far enough that this
would be over 2 min ahead, the registration waits (shown as pending) rather
than send a `ts` the watcher refuses; a watermark more than 6 h ahead can't be
one the watcher accepted and is ignored — and is persisted *before* publishing, so a crash
after the publish can't reuse it; the watcher accepts `ts` up to 6 h old and
2 min ahead and treats anything not newer as stale. The watcher never replies
(a reply would itself be a push), so "registered" means at least one of its
inbox relays accepted the wrap.

*Receiving.* The watcher sends a generic alert (title "Lightning Piggy"; "New
message" / "Zap received" / "New mention" / "Payment received") collapsed per
category (`lp-<category>` as APNs thread/collapse id and FCM tag), with data
`{source: "lp-watcher", category}` (nothing finer — no Nostr kind). What
reaches JS differs: Android in the foreground has the data; an alert the OS
posted while backgrounded is known only by its tag (in expo's
foreign-notification identifier); on iOS expo exposes only `userInfo.body` as
data, so the thread id identifies it. `watcherCategoryOf` checks all three.
On iOS the watcher also sends ONE silent background push when a device first
registers (an admission check, `{source: "lp-watcher", type: "validate"}`, no
alert): it reaches no JS task (the Marmot wake task is registered on Android
only, and drops every watcher payload anyway) and the foreground handler
hides it (`isWatcherValidation`).

* *Foreground:* messages, zaps and wallet activity are suppressed — the open
  app shows them itself (live inbox; `PaymentNotifier` with the real amount).
  Mentions still show: the app has no live mention surface.
* *Payments wording:* NWC notifications are encrypted, so the watcher can't
  tell `payment_received` from `payment_sent`, and its alert says "Payment
  received" either way. The app can't rewrite a background alert (no iOS
  notification service extension; Android notification messages are posted by
  the OS), so instead the Settings copy says plainly that the alert may come
  for a payment you sent, and the alert is suppressed while the app is open —
  which is when in-app payments are made.
* *Taps:* Messages → the Messages list; Mentions → Notifications; Zaps and
  Payments → Wallets tab.
* *Duplicates:* a Marmot welcome is a kind-1059 gift wrap, so the watcher
  announces it as "New message" while Transponder may also wake for it. The
  watcher's "New message" is treated as one of the generic message pings:
  the Marmot wake's "one generic alert at a time" replaces it, showing the
  real Marmot message clears it, and opening the Messages list clears both.
  The Marmot wake task (which sees every push, and taps on Android) ignores
  watcher pushes.

*Per-sender mutes (#1381).* `mutedSenders` persists hex pubkeys per account.
The Notifications list and badge hide muted senders; the shared local-alert
service suppresses their history and OS alerts before scheduling. Message
storage and the Messages inbox keep receiving their DMs. The background
batch detector excludes known muted authors before forming a generic ping.
A received push with `owner` and `senderPubkey` (or a DM's
`conversationPubkey`) is filtered by the presentation handler too.

*Server follow-up:* current watcher alerts contain only a category, and the OS
may display background alert pushes before JavaScript runs. Selective muting
there requires the watcher to honour per-account muted senders server-side,
or provide authenticated owner/sender metadata through a data-only push and
an iOS notification service extension. Do not infer a sender from a category
or a NIP-59 ephemeral wrap author. Undecrypted remote-signer gift wraps and
content-free Marmot wakes have the same limitation until the sender is known;
resolved wrap history rows are filtered once the encrypted DM store identifies
that conversation.

*Privacy.* Apple/Google learn that a notification arrived, when, and — from
the alert itself — which kind (message, zap, mention or payment). For these
categories the watcher additionally learns the user's public key, linked to
the app id and (encrypted) device token, the relays listed, the NWC connection
keys and which wallet service they belong to (Payments), and *when* matching
events arrive. Its subscriptions are visible to the relays it watches: a
relay can see that our server is filtering for the user's key. A registration
that isn't refreshed is deleted after 30 days. It can't read DMs or NWC
traffic (they stay encrypted, and it doesn't try); mentions, zap receipts and
NIP-04 envelopes are public events whose author (and, for a mention, text) it
sees like any relay does. Registrations travel inside gift wraps from throwaway
keys, so relays don't see who registered; the watcher never sees the user's
IP address.

*Known limits.* The watcher can't see DMs on auth-gated inbox relays
(relay.damus.io requires NIP-42 AUTH for kind 1059 — see TROUBLESHOOTING); a
NIP-17 self-copy of a message sent from another device alerts "New message";
anyone can publish a kind 9735, so a forged zap receipt can trigger "Zap
received" (rate-limited by the watcher).

== Market comments, replies and reviews (#1582)

`useSellerActivityChecks` runs bounded, abortable one-shot reads on Notifications
screen focus and 3.5 seconds after app resume (mounted once in `HomeTabs`). It
adds no always-on relay subscription and cancels pending resume work on background
or account change. `sellerActivityService` shares a per-account flight between
these triggers. Reads use at most eight configured relays.

The seller's current kind-30402 coordinates come from the verified seller snapshot,
reduced for deletions, locally hidden listings, status and expiration. Activity
queries chunk 25 coordinates with `limit: 200` and `since`: the saved successful
check time minus a two-minute overlap, capped at 30 days. Comments use uppercase
`#A`; Gamma reviews use `#d` with the `a:` prefix. Replies anywhere use NIP-22
`#p`/`#k`/`#K`, then resolve the actual parent by ID and author (25 at a time,
`since: 0` because the parent may be old). A claimed recipient tag alone never
establishes a reply. Capped queries continue with decreasing, inclusive `until`
bounds (at most 25 pages per filter). Only completed relay snapshots contribute
results; incomplete relays are excluded from subsequent pages of that filter,
but keep the shared checkpoint unchanged so their original range is retried.
Parent lookups also require every requested relay to complete.
Events newer than the requested page are discarded before sorting and limiting.
A saturated timestamp advances to the preceding second and logs the returned
count; additional events within that second may be skipped. Failed/aborted checks
or exhausted page budgets do not advance the checkpoint; consumed IDs and quotas
are preserved for retry.

Event IDs, checkpoints and stranger quotas persist per account. Stranger activity
is limited to 20 entries per listing per delivery day. The existing Only friends
policy suppresses stranger tray alerts while retaining their history; muted senders
are marked seen without recording history or consuming the stranger quota. Rows use icons and never fetch activity authors' avatars
or listing images. The default-on account setting “Comments & reviews on my
listings” controls both history recording and local alerts. History still records
without OS permission when the activity preferences allow it. Lock-screen details use the existing privacy setting.
First-check catch-up older than two minutes, and subsequent catch-up older than a
day, are history-only. History uses source event timestamps so its 200-row cap
retains the newest activity even when catch-up pages arrive newest-first.
History change signals are coalesced before React updates.

An explicit notification tap resolves the current listing and opens root-stack
`ProductDetail` with the Comments or Reviews tab selected. Account changes guard
late resolution. Sellers can reply from any visible comment row; the existing
publisher signs kind-1111 with uppercase listing root tags and lowercase parent
comment tags. Replies render under their parent with bounded row pagination.
