== Testing

This guide covers code quality checks, unit testing, and end-to-end testing for Lightning Piggy.

=== Code Quality

The project enforces code quality through TypeScript, ESLint, and Prettier. All checks must pass before committing.

[source,bash]
----
# TypeScript type checking
npx tsc --noEmit

# ESLint
npm run lint

# Prettier format check
npm run format:check

# Auto-format with Prettier
npm run format
----

=== Unit Testing with Jest

Unit tests run in Node (jsdom) via https://jestjs.io[Jest] with the `jest-expo` preset and https://callstack.github.io/react-native-testing-library/[`@testing-library/react-native`].

**Test files MUST live next to the source as `<file>.test.ts` / `<file>.test.tsx`** (co-located convention). The centralised `tests/unit/` directory is NOT scanned — `jest.config.js`'s `testMatch` is `<rootDir>/src/**/*.test.{ts,tsx}` only. Co-location surfaces missing tests at a glance, keeps tests with their subject when files move, and shortens the relative imports.

For cross-cutting tests (touching multiple files), put them next to the file whose API the test most directly exercises. Example: `src/services/nostrService.test.ts` covers the outgoing wire format; `src/utils/nip17Unwrap.test.ts` covers the incoming parser; `src/utils/syntheticGroupId.test.ts` covers the room-key derivation — even though all three relate to NIP-17 interop.

**Coverage scope:** `src/services`, `src/utils`, `src/contexts` only. Components are excluded (they're tested via Maestro pixel/flow tests instead — mocking Reanimated + bottom-sheet + `expo-image` for unit tests is high-effort, low-payoff).

==== Running Locally

[source,bash]
----
# Run the suite
npm test

# Run with coverage (writes ./coverage/coverage-summary.json plus a
# text summary to stdout — reporters in jest.config.js are
# `json-summary` + `text`; lcov is intentionally off to keep the
# artifact small)
npm run test:coverage

# Watch a single file
npx jest src/utils/foo.test.ts --watch
----

==== Coverage Gate (CI)

The `Coverage` workflow (`.github/workflows/coverage.yml`) runs on every PR to `main`:

. Runs `jest --coverage` on the PR branch.
. Re-runs `jest --coverage` on `main` for the baseline.
. Fails the PR if PR line-coverage drops below main by more than **0.5 percentage points** (the noise floor — small refactors that move lines around shouldn't trip the gate).

The first PR after this infrastructure merges may show a 0% main baseline if `coverage-summary.json` isn't generated yet — that's expected and the gate will pass trivially. Subsequent PRs are then held to the new baseline, so coverage can only steadily increase.

To tighten or loosen the gate, edit `NOISE_FLOOR` in the workflow file.

==== iOS Native Build Gate (CI)

`modules/nostr-native` has two macOS jobs in `.github/workflows/ci.yml`:

* *iOS engine lifecycle* — compiles `NostrEngine.swift` against hand-written SDK doubles (`scripts/ios-tests/`) and runs the disposal/restart race test. Fast, but it proves nothing about the real rust-nostr bindings or ExpoModulesCore.
* *iOS native pod build* — the real thing: `npm ci` with `FETCH_NOSTR_SDK_SWIFT_REQUIRED=1` (the postinstall must fetch and checksum-verify the pinned 0.44.2 `nostr_sdkFFI.xcframework` + `NostrSDK.swift`, never take the JS-only "continue without" path), `npx expo prebuild --platform ios` (which runs `pod install`), then a Debug `xcodebuild` of the whole app for an iOS Simulator, with Xcode pinned to the release `TROUBLESHOOTING.adoc` validates (`XCODE_VERSION` in the job). It fails if prebuild rewrote `package.json` / `package-lock.json`, if `Podfile.lock` lacks `NostrNative (0.44.2)`, or if no `uniffi_nostr_sdk_ffi_` symbols were linked into the app.

The pod-build job runs on every PR with no path filter, so it can be a required check. Marking it required happens in GitHub settings, not in this repo: a maintainer adds `iOS native pod build` under branch protection for `main` → required status checks. When you bump the rust-nostr Swift SDK, update the version in `scripts/fetch-nostr-sdk-swift.mjs`, the podspec, and the two `0.44.2` checks in the job together.

==== Picking What to Cover Next

Use `scripts/coverage-priorities.sh` to get a prioritized list of files most worth testing:

[source,bash]
----
# Generate coverage data first (otherwise every file ranks as 0% covered)
npm run test:coverage

# Top 20 ranked files (default)
./scripts/coverage-priorities.sh

# Top 50
./scripts/coverage-priorities.sh 50
----

The ranking heuristic is `(churn × loc × fanout) / (coverage% + 1)`:

* **churn** — distinct commits in the last 90 days (changes often → likely to regress)
* **loc** — file size (more behaviour → more to break)
* **fanout** — how many other src files reference this one (blast radius)
* **coverage** — already-tested files drop down the list

Pick from the top of the list. The script prints rank, score, and the underlying counts so you can see *why* a file ranked where it did.

=== E2E Testing with Maestro

End-to-end tests use https://maestro.mobile.dev[Maestro], a mobile UI testing framework. Tests are written in YAML and interact with the app through accessibility labels and test IDs.

==== Setup

[source,bash]
----
# Install Maestro
curl -Ls "https://get.maestro.mobile.dev" | bash

# Verify installation
maestro --version
----

Ensure the app is built and running on a connected device or emulator before running tests.

==== Running Tests

[source,bash]
----
# Run a single flow
maestro test .maestro/authentication/flow-006-login.yaml

# Run a whole feature area (numbered flows only)
maestro test .maestro/payments/

# Run the curated wallet/transfer suite (skips the un-numbered helpers
# under common/ and the perf flows, which aren't standalone-runnable)
source .env && bash .maestro/reporting/run-all.sh
----

NOTE: Don't run `maestro test .maestro/` over the whole tree — that
sweeps in the shared building blocks under `.maestro/common/` (and the
`perf/` flows), which are designed to be pulled in via `runFlow:` and
fail when executed on their own. Target a feature-area folder, a single
flow, or the `run-all.sh` runner instead.

==== Marmot (MLS) E2E: flows 124–130 + the peer bot

The Marmot flows under `.maestro/messaging/` need a second Marmot client on
the other end. `scripts/marmot-peer-bot.mjs` is that client: a Node script on
`marmot-ts` (with its own WebCrypto provider, so it also cross-checks the
app's pure-JS Hermes crypto over the wire) that signs in as a Piggy fixture,
publishes a key package, joins any Welcome it receives and answers every
message with `pong: <text>`. It logs what it decrypted (`RECV kind=…`,
`MEDIA OK v=encrypted-media-v2 …`), which is how a run proves content went
over MLS rather than NIP-17. Its MLS state persists per identity in
`~/.cache/lp-marmot-bot/<pubkey>/`, so it stays a member of groups it joined
in earlier runs.

[cols="1,3",options="header"]
|===
| Bot env var | Effect

| `MAESTRO_NSEC_BOT` | Required: the fixture to run as (e.g. `$MAESTRO_NSEC_LITTLE`).
| `BOT_INITIATE_TO` / `BOT_INITIATE_TEXT` | Start a White Noise-shaped DM to that hex pubkey (if none exists) and send the text.
| `BOT_SEND_PHOTO` (+ `BOT_PHOTO_CAPTION`) | With `BOT_INITIATE_TO`: send that image file the White Noise way (kind 9 + `imeta`, encrypted-media-v2).
| `BOT_RESET=1` | Forget the bot's MLS state first (as if reinstalled), e.g. to force a fresh invite.
| `BOT_MINUTES` | How long to stay up (default 15).
| `BOT_DEBUG=1` | Also log every kind-445 event seen.
|===

`scripts/marmot-e2e.sh` runs the flows end to end: it starts and stops the
bot(s) per flow, runs Maestro against the LP emulator signed in as Big
Piggy, and asserts the bots' logs. Each run tags its messages with a unique
`RUN_TAG`, so a flow can't pass on bubbles left by an earlier run.

[source,bash]
----
bash scripts/marmot-e2e.sh            # 125 126 127 128 129 130
bash scripts/marmot-e2e.sh 127 129    # a subset
----

Needs `.env` with `MAESTRO_NSEC_{BIG,LITTLE,MIDDLE}`, Big following Little
and Middle, Maestro on `PATH`, ImageMagick (`convert`, for flow 130) and
`DEVICE` (default `emulator-5554`).

[cols="1,3",options="header"]
|===
| Flow | Coverage

| `flow-124-dm-protocol-picker` | Picker offers NIP-17 / Marmot (Alpha) / NIP-04; sends one NIP-04 DM into its own thread. No bot needed.
| `flow-125-marmot-dm` | First Marmot DM to Little: creates the 1:1 MLS group and invites the bot.
| `flow-126-marmot-group` | Creates a named Marmot group with Little; the row carries the Marmot pill.
| `flow-127-marmot-dm-message-types` | Contact, location, GIF, poll (kind 1068), photo (MIP-04 v2) and invoice over Marmot; the runner asserts each inner kind in the bot log.
| `flow-128-marmot-three-pigs-group` | Big, Little and Middle (two bots) in one group; rename, then remove Middle, who must stop receiving.
| `flow-129-marmot-receive-invite` | The bot (as Middle) invites Big; Big auto-joins from the Welcome and replies over MLS.
| `flow-130-marmot-photos` | Photos both ways: the bot's White Noise-format photo renders; ours is decrypted by the bot.
|===

Run flows 127 and 130 after 125 (they reuse its DM). The flows only ever
message Piggy fixtures.

==== Signer matrix E2E: flows 131–135 (nsec / Amber / NIP-46)

LP signs and decrypts through three signer backends (`signerType` in
`NostrContext.tsx`), and each has its own failure modes — Amber's Intent
round-trips and prompts, NIP-46's relay round-trips and a remote side that can
say no or say nothing. The signer matrix runs real flows through each one, one
Piggy fixture per signer:

[cols="1,1,2",options="header"]
|===
| Piggy | Signer | Set up by

| Big Piggy | `nsec` | `MAESTRO_NSEC_BIG` — the device default
| Middle Piggy | Amber (NIP-55) | Amber on the emulator holding `MAESTRO_NSEC_MIDDLE` (`flow-131`)
| Little Piggy | NIP-46 | `scripts/nip46-test-bunker.sh` on the host holding `MAESTRO_NSEC_LITTLE`
|===

[cols="1,3",options="header"]
|===
| Flow | Coverage

| `authentication/flow-131-amber-import-middle` | One-time setup: imports Middle's key into a fresh Amber ("Approve basic actions").
| `authentication/flow-132-signer-matrix-smoke` | Logs in as each Piggy with its signer, checks Home + the drawer identity, restores Big.
| `messaging/flow-133-marmot-big-nsec-middle-amber` | Big → Middle NIP-17 (Middle unwraps via Amber); Middle's first Marmot send (Amber signs the key package + seals the Welcome); Big creates a Marmot group with Middle; Middle joins via Amber and replies; Big sees it.
| `messaging/flow-134-nip17-dm-nip46-approve-decline-timeout` | Little (NIP-46) reads Big's NIP-17 DM and replies with the bunker approving, declining (bubble must settle to "Send failed") and never answering (LP's 20 s send watchdog must flip it to "Send failed"); Big receives only the approved reply.
| `authentication/flow-135-nip46-pairing-timeout` | Bunker ignores the pairing → after LP's 120 s wait the sheet shows "Pairing took too long — try again" and Big is still signed in. Slow; not in the default run.
|===

===== One-time setup

. *Amber* — install the latest release from
  https://github.com/greenart7c3/Amber/releases[greenart7c3/Amber] (x86_64 APK
  for the emulator) and verify it first: `gpg --verify manifest-vX.txt.sig
  manifest-vX.txt` against key `44F0AAEB77F373747E3D5444885822EED3A26A6D`,
  `sha256sum` against the manifest, and `apksigner verify --print-certs` against
  the README's certificate fingerprint (`E8:AB:8C:69…:BF`). Then
  `adb -s emulator-5554 install amber-x86_64-vX.apk` and
  `bash scripts/signer-matrix-e2e.sh setup-amber`. Amber must hold only
  Middle's key.
. *NIP-46 bunker* — nothing to install: `scripts/nip46-test-bunker.mjs` is a
  small NIP-46 remote signer on `nostr-tools` (already a dependency). The runner
  starts and stops it. `nak bunker` handles the same `nostrconnect://` pairing
  but can't decline or ignore single methods, which the DECLINE / TIMEOUT cases
  need.

===== Running

[source,bash]
----
bash scripts/signer-matrix-e2e.sh            # 132 133 134
bash scripts/signer-matrix-e2e.sh 134 135    # a subset; 135 = slow pairing timeout
DEVICE=emulator-5556 OUT=/tmp/sm bash scripts/signer-matrix-e2e.sh
LOCK_FILE=/path/to/emulator.lock bash scripts/signer-matrix-e2e.sh   # shared emulator
----

The runner refuses non-emulator serials unless `SIGNER_MATRIX_ALLOW_DEVICE=1`.
Per flow it prints the Amber prompts the flow had to answer, and at the end the
bunker's request counts — the quickest way to spot a prompt storm.

Driving the bunker by hand (the flows do this through its control API via
`.maestro/common/nip46-bunker.js`):

[source,bash]
----
bash scripts/nip46-test-bunker.sh start             # Little Piggy, mode=approve
bash scripts/nip46-test-bunker.sh mode decline      # approve | decline | silent | decline-all | silent-all
bash scripts/nip46-test-bunker.sh pair-from-screen  # decode LP's pairing QR on $NIP46_DEVICE and answer it
bash scripts/nip46-test-bunker.sh status            # {"mode":…, "counts":{"sign_event:kind=13":1, …}}
bash scripts/nip46-test-bunker.sh log
bash scripts/nip46-test-bunker.sh stop
----

`decline` / `silent` apply to `sign_event` and the `*_encrypt` methods only, so
the session and inbox decrypts keep working. The `-all` variants also cover the
decrypts and new pairings. The session handshake (`connect`, `ping`,
`get_public_key`, `switch_relays`) is answered in every mode, so an existing
pairing stays alive.

The control API is bound to `127.0.0.1` and needs the bunker's per-start token
(`$XDG_RUNTIME_DIR/lp-nip46-bunker-<uid>/token`, mode 0600); the runner exports
it as `MAESTRO_NIP46_TOKEN` for the flows. Pairing URIs may only name
allow-listed relays.

===== Counting signer prompts (PR #1177 push registration)

#1177 promises that remote signers are only asked on a user action — one
signature (a kind-451 owner proof) per Marmot group when push is enabled /
"Finish setup" runs, and nothing on app start or in background passes. With
#1177 checked out on the device:

* *NIP-46*: `bash scripts/nip46-test-bunker.sh reset-stats`, log in as Little
  (`common/login-nip46-little.yaml`), enable *Account → Security → Message
  notifications via push (Marmot)*, then `status`: `sign_event:kind=451` must
  equal Little's Marmot group count. Restart the app and wait — the counter must
  not move. Decline path: `mode decline` before enabling; enabling must stop at
  the first decline (`verdict:decline` = 1).
* *Amber*: log in as Middle (`common/login-amber-middle.yaml`), enable push and
  answer with `common/approve-amber-prompt.yaml`; the runner-style count of
  `Tap on "Accept"` lines in Maestro's `maestro.log` is the prompt count (one
  per group). Rejecting the first prompt must stop the pass.

==== Writing Tests

IMPORTANT: Never use coordinates (`point:`, `tapOn: { point: }`, `adb shell input tap`) in Maestro tests. Coordinates are fragile and break across screen sizes, devices, and OS versions.

Instead, always use accessibility-based selectors:

[cols="1,2,2", options="header"]
|===
| Selector | Usage | Example

| `id:`
| Match by `testID` prop
| `id: 'tab-friends'`

| `text:`
| Match by visible text or `accessibilityLabel`
| `text: 'Friends tab'`

|===

If a component is missing an accessibility label, add one to the source code rather than working around it with coordinates.

===== Composable Subflows

Subflows are reusable Maestro flows that live un-numbered in `.maestro/common/` (e.g. `common/login-as.yaml`). They aren't standalone tests — callers `runFlow:` them (via a relative path, e.g. `../common/login-as.yaml`) as a step inside a regular flow, so they're skipped by a feature-area run and must never be run on their own. Use them whenever multiple flows share a setup walk.

Available subflows (all under `.maestro/common/`):

[cols="2,3", options="header"]
|===
| Subflow | Purpose

| `common/login-as.yaml`
| Force-stop the app, sign out any prior session, then sign in via the nsec passed in `MAESTRO_NSEC_BIG`. Used by every multi-actor flow.

| `common/seed-test-wallet.yaml`
| Walk the AddWalletWizard to seed a test wallet so wallet-conditional tests (Send, Receive, Transfer, cached-tx, etc.) don't have to re-implement the wizard inline. Picks the wallet type based on which env var is non-empty:

`MAESTRO_TEST_NWC` → Lightning (NWC) wallet via connection string. +
`MAESTRO_TEST_MNEMONIC` → On-chain hot wallet via 12/24-word seed phrase. *Requires dev mode enabled in the app* — run `authentication/flow-004-login-dev.yaml` once first.

Required `WALLET_NAME` sets the alias shown on the wallet card. The flow asserts that alias appears in the carousel before returning. Maestro's `${VAR}` interpolation has no robust default-fallback across versions, so an unset value leaves the literal `${WALLET_NAME}` in the alias field and the visibility assertion never matches — pass it explicitly via `runFlow.env`.

|===

Example invocation from a wallet-conditional test:

[source,yaml]
----
- runFlow: ../common/login-as.yaml
- runFlow:
    file: ../common/seed-test-wallet.yaml
    env:
      MAESTRO_TEST_NWC: ${MAESTRO_NWC1}
      WALLET_NAME: "Seeded NWC"

# ... continue with wallet-dependent assertions ...
----

The required env vars (`MAESTRO_TEST_NWC`, `MAESTRO_TEST_MNEMONIC`) live alongside the rest of the Maestro fixtures in `.env.example`. Leave them blank in your local `.env` if you don't run wallet-conditional flows.

=== Screenshots

Capture screenshots from a connected Android device using ADB:

[source,bash]
----
# Capture screenshot
adb exec-out screencap -p > /tmp/screen.png

# Resize for high-DPI devices (> 2000px)
convert /tmp/screen.png -resize 1200x1200\> /tmp/screen_small.png
----

The `\>` flag ensures ImageMagick only shrinks images that exceed 1200px — smaller images are left unchanged.
