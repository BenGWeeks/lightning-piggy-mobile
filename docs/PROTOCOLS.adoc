== Nostr Protocol State

This page documents which Nostr Improvement Proposals (NIPs) Lightning Piggy Mobile implements, in which direction (send / receive), and any deprecation timelines.

=== DM Protocol State

==== Summary

Lightning Piggy ships **NIP-17 gift-wrapped DMs** (kind-1059 → 13 → 14) as the **default** outbound 1:1 messaging path. Legacy **NIP-04** (kind 4) events are **read** for backward-compatibility with peers on older clients; one is only sent when the user explicitly picks NIP-04 in a thread's protocol picker. Group chats also use NIP-17 (a multi-`p`-tag kind-14 rumor). **Marmot** (MLS over Nostr, Alpha) is a third, opt-in transport for 1:1 and group chats — see <<marmot-protocol>>.

[cols="1,1,1,3", options="header"]
|===
| Direction | NIP-04 (kind 4) | NIP-17 (kind 1059 → 13 → 14) | Notes

| Send (1:1 DM) | ❌ removed | ✅ only path | `sendDirectMessage` in `src/contexts/NostrContext.tsx`
| Send (group) | n/a — never supported | ✅ only path | `sendGroupMessage` in `src/contexts/NostrContext.tsx`
| Receive (display) | ✅ kept | ✅ kept | `fetchConversation`, `refreshDmInbox` query both kinds and merge into one thread sorted by the rumor's `created_at`
|===

==== Why NIP-17

* NIP-04 is marked `unrecommended` at the top of the NIP itself. AES-256-CBC, no metadata protection — sender pubkey, `created_at`, recipient `p` tag are all on the wire in plaintext.
* NIP-17 wraps each kind-14 rumor in a kind-13 seal inside a kind-1059 gift wrap. The outer wrap exposes only a random ephemeral pubkey, a `created_at` randomised up to 2 days in the past, the `kind: 1059` tag, and the recipient `p` tag. Sender identity, message kind, true send time, and any tags on the rumor are all hidden from relays and observers.
* Encryption throughout NIP-17 is **NIP-44** v2 (secp256k1 ECDH → HKDF → ChaCha20 + HMAC-SHA256).

==== Send path (outgoing)

* Inner rumor is built by `createDirectMessageRumor` (1:1) or `createGroupChatRumor` (groups) — both produce a `kind: 14` event with a `pubkey` field but no signature.
* `sendNip17ToManyWithNsec` (nsec signer) seals + wraps the rumor for each recipient via `nostr-tools` `nip59.wrapManyEvents`, which also wraps for the sender so the message lands in the user's own inbox on other devices.
* `sendNip17ToManyWithSigner` (Amber signer) does the same SEQUENTIALLY because Amber's native module rejects concurrent intents with `BUSY`. Per recipient: 1× `nip44Encrypt` + 1× `signEvent` for the seal; the gift wrap is signed locally with a fresh ephemeral key (never the user's key) so it does not need a signer round-trip.
* The `BUSY` guard only holds while Amber can still answer. A request whose result never comes back (Amber hands focus to another app, or never opens) is settled as `NO_RESULT` when Lightning Piggy returns to the foreground, or by a launch watchdog if Lightning Piggy still holds window focus. Late results carry a per-launch request code (never reused while the abandoned Amber activity could still answer) and are ignored, so they can't settle a newer request. `src/services/amberErrors.ts` maps the native codes to declined / no-response / busy / unavailable copy (#1186).
* Wraps are published in parallel via `pool.publish` to the union of the user's NIP-65 write relays and `DEFAULT_RELAYS`.

==== Receive path (display)

The Messages tab fetches both protocols on focus and on conversation open:

* `fetchInboxDmEvents` queries three filters in parallel:
+
[source]
----
{ kinds: [4],    authors: [me] }   // outgoing legacy DMs
{ kinds: [4],    '#p':     [me] }   // incoming legacy DMs
{ kinds: [1059], '#p':     [me] }   // gift wraps addressed to us
----
* Kind-4 events are NIP-04-decrypted with the appropriate signer (`nip04.decrypt` for nsec, Amber's `nip04Decrypt` IPC for Amber) and merged into the per-peer thread.
* Kind-1059 wraps are unwrapped via `unwrapWrapNsec` (nsec) or `unwrapWrapViaNip44` (Amber) — both perform the full NIP-17 verification chain: signature check on the wrap, NIP-44-decrypt the wrap to a kind-13 seal, NIP-44-decrypt the seal to a kind-14 rumor, and assert `rumor.pubkey === seal.pubkey` (the spec MUST that prevents sender-spoofing on a tampered rumor).
* `classifyRumor` then routes 1:1 rumors into the per-peer DM thread and multi-recipient rumors into the matching group room.
* *Reactions in 1:1 NIP-17 chats* (#1319, #1321) travel like the messages: a kind-7 rumor (`content` = the emoji; `e` = the target rumor id, `p` = its author, plus the peer when reacting to your own message; `k` = `14`) and a kind-5 retraction (`e` = the reaction's rumor id, `k` = `7`, `p` = the peer), gift-wrapped to the peer and to yourself. Nothing is published publicly: a public kind 7 would expose the private rumor id, the chat partner and the time. This matches Amethyst and Anagram. Received reaction rumors are stored as `wire_kind` 7 / 5 rows and shown as pills on their target, never as bubbles, inbox previews or notifications. Your own public kind-7 DM reactions from older builds are still read (by author and `k`, so no private rumor id is sent to a relay) and shown after the stored ones; retracting one also sends a public kind 5 asking relays to delete it. A peer's old public reactions are not read, since finding them would mean querying relays for the chat's message ids. Reactions or retractions you send from another client on the same account are placed by the message or reaction they name when they carry no peer `p` tag. NIP-04 threads keep public NIP-25 reactions (the kind-4 messages are public events already).
* Threads sort by the **rumor's** `created_at`, never the gift wrap's (the wrap timestamp is intentionally fake per the spec).

==== Deprecation timeline for NIP-04 reads

We will keep the kind-4 read filter and the `nip04.decrypt` codepath until both of:

. The user research signal that no active contacts are still on NIP-04-only clients (Damus is the relevant laggard at the time of writing).
. The kind-4 plaintext cache (`nip04PlaintextCache` LRU + the per-thread persisted cache) for a representative active user shows zero new fresh-decrypt entries for at least 90 days, evidenced by the `[Perf] fetchConversation` log line `k4=N (hits=0, fresh=0)`.

There is no scheduled removal date. Removal will be announced one release ahead in the GitHub Release notes and the read filter will land behind a feature flag for one release before the codepath itself is deleted.

==== Interop notes

* **Damus** (as of April 2026 master) does not subscribe to kind 1059 — its `HomeModel` filter is kind-4-only. A message Lightning Piggy sends to a Damus-only peer will not appear in their UI until Damus ships NIP-17. Other major clients (Amethyst, 0xchat, Snort, Coracle, Primal) accept NIP-17 and will display Lightning Piggy's outgoing DMs.
* The `subject` tag on a kind-14 is what 0xchat / Amethyst / Quartz read to display the conversation title — `createGroupChatRumor` always emits one; `createDirectMessageRumor` deliberately omits it (a 1:1 thread has no name). See issue #271 for the cross-client subject-tag interop work.
* Lightning Piggy does **not** publish a kind-10050 NIP-17 DM relay-list event. We rely on the user's existing NIP-65 write-relay list plus the DEFAULT_RELAYS fallback. If a recipient publishes their own kind-10050 we do not currently honour it — they must accept wraps on at least one relay we publish to.

==== Direct chat versus a two-person named group (#1599)

NIP-17 defines a room by the sender plus the deduplicated `p`-tag participant set;
`subject` names or renames that room and is optional on later messages.
Lightning Piggy exposes both a direct chat and a named two-person group for the
same participants, which that wire identity cannot distinguish on its own.
The app therefore applies this explicit routing policy to newly ingested rumors:

* Exactly one other participant and no valid nonempty `subject`: direct chat,
  even when the group registry contains the same membership.
* A valid `subject`, or two or more other participants: group routing by the
  participant set. A changed subject renames a synthetic room; it is not a new id.
* Group text and file sends include `subject` on every rumor. There is no separate
  app-specific group/room tag. Direct sends omit it. Marmot routing is unchanged.

Compatibility trade-off: a two-person group message from another client such as
0xchat or Amethyst that omits `subject` is indistinguishable from a direct message
and now appears in the direct chat. This is an app policy, not a NIP-17 requirement.
Groups with three or more participants still route by membership without a subject.
Multiple named groups with identical membership are not given distinct wire identities.

A one-time per-account repair re-fetches legacy two-person NIP-17 group wraps
in batches of 20 and unwraps them with the account signer. Only authenticated
subjectless two-party text/file rumors move to the direct thread. The direct
store is written first (deduplicated by wrap or rumor id), then the group copy
is removed. Marked groups, larger rooms, optimistic group sends and Marmot
are preserved. Missing wraps, denied decrypts and interruption leave the done
flag unset for retry; rows without a verifiable original rumor stay in place.
The repair uses the yield scheduler and persists completion per account.

=== Marmot (MLS over Nostr) — Alpha

A third DM/group transport using the vendored Marmot v2 library; White Noise interoperability depends on the client version and protocol profile; no tested version/profile is specified here. Full design in `SOLUTION_DESIGN.adoc` → "Marmot (MLS) messaging — Alpha". The library is `@internet-privacy/marmot-ts`, pinned to a build of upstream PR #83 (encrypted media v2).

[cols="1,3",options="header"]
|===
| Kind | Use

| 30443 | Key package (addressable; `d` = a random 32-byte hex slot per account per installation, kept across sign-out, `client` = `Lightning Piggy`), published to the NIP-65 write relays. Advertises the `0x800b` encrypted-media-v2 component, which White Noise requires.
| 450 (local-only) | Account-identity proof embedded in each MLS leaf, binding the leaf's signature key to the Nostr account. Signed by the account key alongside every key package; never published.
| 444 | Welcome (group invite), NIP-59 gift-wrapped to the invitee's kind-10050 inbox — unwrapped by the NIP-17 inbox path (follow gate applies) and routed by `marmotWelcomeRouter`.
| 445 | Group event (MLS commits + application messages), `h`-tagged with the Nostr group id; signed by per-message ephemeral keys.
| 1059 → 446 | MIP-05 push trigger: a kind-446 rumor (concatenated encrypted device tokens, `["v","marmot-push-v1"]`) gift-wrapped to a notification server.
| 1059 → 8480 | Notification-watcher registration (not Marmot): a kind-8480 rumor whose JSON content either registers this device (`action: "register"` — app, platform, push token, `apns_env` on iOS, categories, relays, NWC proofs, `ts`) or unregisters it (`action: "unregister"` — app, platform, token and `ts` only; removes the device's registration whatever its categories), gift-wrapped to Lightning Piggy's watcher (seal signed by the user). See `docs/architecture/notifications.adoc` → "The notification watcher" and the watcher's `PROTOCOL.md`.
| 9 (inner) | Chat text. With an `imeta` tag, a MIP-04 photo or voice note (`audio/mp4`). A GIF is the GIPHY URL plus a `via GIPHY` line. A quoted reply carries `e` + `q` tags naming the parent. In groups an @mention is a `nostr:npub…` reference in the content plus a `p` tag per mentioned member (#1295); group messages carry no roster `p` tags or `subject` (older builds sent both, so a kind 9 with a `subject` tag has no mention tags).
| 7 / 5 (inner) | Reaction (`content` = emoji, `e` = message id) and its retraction (`e` = reaction id), in 1:1 Marmot threads. A kind 5 naming a message is "delete for everyone" (sent for your own messages, applied from the author).
| 1009 (inner) | Edit: one `e` tag naming the original, `content` = the new text. Honoured only from the original's author; latest wins.
| 4891 (inner) | Admin removal of a message in a group (`{"v":1,"action":"remove"}`), applied.
| 447 / 448 / 449 (inner) | MIP-05 push-token update / list / removal, gossiped by group members. Kept as push state, never shown. We publish 447 (our own record) and 449 when push is on / turned off; we never send 448 or empty 447 requests.
| 451 (local-only) | MIP-05 owner proof that each push record's signature covers. Never published.
| Other inner kinds | 15 (files), 1068 (polls), 16/17 (orders), NWC shares: the same rumor NIP-17 carries, unchanged.
|===

Inner events are unsigned rumors (MLS authenticates the sender). Inner kinds that aren't messages — 5, 7, 447–449, 1009 (edit), 1200–1202, 1210, 1984, 1985, 4891 — are never stored as chat rows.

==== MIP-04 encrypted media

A photo is a kind-9 event with an `imeta` tag (`encrypted-media-v2`; v1 is still read). The blob on Blossom is ChaCha20-Poly1305 ciphertext; its key is derived from the MLS group's epoch secret and the `imeta` fields, so the key never travels in the message and can only be *derived* while that epoch's state is retained. The receiver derives one candidate key per retained epoch on arrival and stores them (in `mediaKeys:<group>` and the stored message row), so an already-received photo stays decryptable on this device after the epoch is gone, until those copies are deleted. It verifies both the plaintext and ciphertext SHA-256 on decrypt. Only a public-https Blossom URL that commits to the ciphertext hash is fetched. Ciphertext is uploaded as `application/octet-stream`, with fallback servers for Blossom hosts that refuse it (HTTP 415).

==== MIP-05 push notifications

Members publish encrypted native push tokens inside the group (447/448, removals 449; ≤32 entries, `v` = `marmot-push-v1`). Each entry is checked against its owner's kind-451 signature and ordered per (member, leaf, platform, server) by `(owner_ts, SHA-256(SignedRecord))`, with removal tombstones. After sending a kind 9 or 1068, the app gift-wraps the other members' tokens (≤19 per wrap) as kind-446 triggers to each token's notification server, published only to the records' relay hints and the server's own kind-10050 inbox. The server decrypts the token and sends a content-free push. With the opt-in receive side on, the app seals its own native FCM/APNs token to Lightning Piggy's notification server (per-app-id Transponder) and publishes it as a kind-447 self-update in each group, with a kind-451 owner proof signed by the user; turning it off publishes 449 removals. Details — token encryption, owner-proof checks, when a remote signer is asked — in `SOLUTION_DESIGN.adoc` → "Marmot (MLS) messaging".

==== Fallback and interop

* A 1:1 send to someone with no usable key package (none, expired, or a legacy MDK 0.8 one from the classic White Noise app) is offered over NIP-17 instead: the app asks first, and only if the user agrees does the thread switch to NIP-17 before the send is attempted. Cancel or dismiss sends nothing and keeps the draft; after a successful send, the app attempts a one-time note to the peer that Marmot was tried (`marmotFallback.ts`, `useConversationComposerActions.ts`).
* Key packages are read from the peer's NIP-65 write relays plus the lookup relays. Selection keeps the newest event per `d` slot, skips retired slots and validates signature, tags, lifetime and credential. Fresh packages must advertise `0x800b`: the window is 35 days for White Noise-tagged packages, 14 otherwise. If none is fresh, the single newest compatible package is selected, or the newest valid package if none is compatible. A new 1:1 with a selected White Noise package uses only the newest such package; other invites use the selection in one commit, skipping packages that fail group eligibility or invite checks and capping accepted devices at 10 per person. An existing 1:1 later adds devices the contact installed since it began (fresh key packages whose leaf signature key isn't in the group yet, one commit; White Noise contacts get only their newest White Noise install), #1559. Linking your own installs (historical MIP-06 device linking) isn't implemented; see `SOLUTION_DESIGN.adoc` → "Key packages" for the exact checks.
* Every commit Lightning Piggy sends, including the founding invite, carries a GroupContextExtensions proposal that puts `app_data_dictionary` last, as MDK expects, so a rename or admin change doesn't fork White Noise off the group (#1309).
* Typing indicators (ephemeral, content-free) are not carried over MLS. Live location is (#1300): in a Marmot chat the markers and coordinate updates are MLS application messages — see the next section.

=== Live location: tagged markers + coordinate updates (#206, #1300)

A share is a *start marker*, a stream of *coordinate updates*, and an *end marker*. Markers ride the chat's own transport; updates depend on it.

[cols="1,3",options="header"]
|===
| Part | Wire format

| *Start / end marker* (any chat)
| An ordinary chat message — NIP-17 kind 14, or Marmot kind 9 in a Marmot 1:1 or group. The `content` is readable text for other clients: `📍 Sharing my live location for 1 h` (or `📍 Live location ended`) and a `https://maps.google.com/maps?q=<lat>,<lon>` link, which White Noise draws as its native map card. The machine-readable part is a tag, `["live-location", "start"\|"end", <sessionId>, <startedAt ms>, <durationMs>, "geo:<lat>,<lon>;u=<acc>"]` (geo empty on an end with no fix), plus a NIP-31 `alt` tag. A NIP-17 start also carries `["live-location-key", <session pubkey>, <32-byte secret hex>]`. `textForRumor` stores a tagged marker as the internal sentinel text (`[live-location:start]` + JSON + `geo:` block) that the bubble renders; previews show a label, never the stored marker.

| *Updates — Marmot*
| Inner app event kind 20069 (NIP-01's ephemeral range: "not expected to be stored") inside a normal kind-445 MLS application message; `content` = JSON `{ sessionId, lat, lon, accuracy, heading, ts }`, no tags. MLS gives end-to-end encryption and sender authentication (the receiver trusts only the start marker's sender), so no NIP-04 and no `p`/`d` metadata. Receivers never store them as rows, the session keeps them out of the durable rumor history (whose newest-500 window protects real messages) and out of the delivered-dedupe cache. Option (b) — an ephemeral *outer* event — was rejected: Marmot group traffic is kind 445 only, and a NIP-40 `expiration` tag is only allowed when the group's retention component is on.

| *Updates — NIP-17*
| Ephemeral kind 20069, signed by the share's *session key* (from the start marker), *no tags*, `content` NIP-44 v2 encrypted with the start marker's secret as the conversation key. Relays learn neither sender, recipient nor session; neither side needs a signer (Amber / NIP-46 work in the background). Receivers subscribe with `authors=[session pubkeys]`. Shares from older builds (author-signed, `p` + `d` tags, NIP-04) are still received.
|===

*Cadence.* An update goes out when the sharer moved ≥ 25 m and ≥ 30 s passed since the last, or as a heartbeat when still — every 2 min on NIP-17, 5 min on Marmot (its updates are stored kind-445 events). Worst case for an 8 h Marmot share moving non-stop: 960 events (about 1 MB on relays); still: 96.

*Background.* `startLocationUpdatesAsync` + a TaskManager task: an Android location foreground service (plus an ongoing "Sharing your location with … · Stop sharing" notification), iOS `UIBackgroundModes: location` with the blue indicator. Both need only "While in use". Without them the share falls back to the foreground-only watcher and pauses in the background.

Durations are capped to `MAX_DURATION_MS` (8 h) at parse time. Sessions are scoped to the sender's pubkey; an account switch or sign-out stops the share, and that account's next start sends the end markers. See `liveLocationWire.ts` (wire format), `liveLocationPolicy.ts` (cadence), `liveLocationSender.ts`, `liveLocationTracker.ts`, `liveLocationUpdateStore.ts` (coalesced receiver) and `LiveLocationContext.tsx`.

=== Sharing rich objects in a DM: the publish-and-reference pattern (interop)

Recurring question: to share a contact / calendar event / location / poll *inside* a DM and have other clients (Amethyst, Damus, …) render it, do we wrap a dedicated event kind inside NIP-17? *No.* The interoperable Nostr pattern is **publish-and-reference**: the object is published as its own standard event, and the DM only carries a `nostr:` *pointer* to it (NIP-21 / NIP-27) in the kind-14 `content`. The receiving client resolves the pointer and renders the appropriate embedded card. Confirmed against Amethyst's `quartz` (it parses `nostr:naddr`/`nevent`/`nprofile` out of content and renders the referenced event).

[cols="1,2,2",options="header"]
|===
| Object | Published as its own event | Referenced in the kind-14 as

| Contact / profile | kind 0 (already exists) | `nostr:nprofile…` in content (no `p` tag — see below)
| Calendar event | kind 31922 (date) / 31923 (time) — NIP-52, addressable | `nostr:naddr…` in content + `q` tag
| Note / post | kind 1 | `nostr:nevent…` + `q` tag
| Article | kind 30023 | `nostr:naddr…` + `q` tag
| Location (a point) | *no standard kind exists* | best-effort only — see below
|===

Two hard constraints:

* *The referenced object is public.* The DM envelope stays private (the pointer is inside the encrypted kind-14), but the referenced event is a normal published event anyone can fetch with the `naddr`/`nevent`. There is **no interoperable way to share a _private_ rich object**: per NIP-17, other clients only unwrap kinds *14 (chat), 15 (file), and 7 (reaction)* from a gift wrap — a gift-wrapped kind-31923 or kind-1068 is invisible to them. Private + rich + interoperable: pick two.
* *Tag rules differ inside a kind-14.* Referencing an **event** → add a `q` (quote) tag (safe, conventional). Referencing a **profile** → content only, *never* a `p` tag — in NIP-17 the kind-14 `p` tags are the chat participants, so tagging a mentioned person would add them to the conversation and re-route a copy to them.

*Location is the genuine exception.* There is no location *event kind* anywhere in the NIPs — NIP-52 carries location as a `location` string tag + a `g` geohash tag on a calendar event, and Amethyst's own "location" is geohash-tagged notes (NIP-73 geohash scope) + a geohash feed. So there is no published "location object" to point an `naddr` at, and the best-effort for a point in a DM is a `geo:` URI in the `content` (a client that decrypts the DM may linkify it). A live, moving pin in a DM is therefore *inherently app-specific* — which is exactly why the live part of our live location is a private convention (a `live-location` tag + kind-20069 updates) — though its markers now read as an ordinary location message with a maps link in every client. Polls (NIP-88) are public-only for the same family of reasons (votes must be public to tally), so our `[POLL]` DM encoding is likewise app-private by necessity.

*Why not add a `g` geohash tag to the markers?* Because inside NIP-17 the kind-14's tags are encrypted (the rumor is sealed + gift-wrapped), a `g` tag would be *private* — but that also means relays never see it and so cannot index it. The whole purpose of a `g` tag is relay-side `#g` discovery (geohash feeds), which is impossible on an encrypted rumor. So the tag would add no discovery value and ~no rendering value over the `geo:` URI already in the body. It is **not** worth adding. (Geohash tags *are* best practice on *public* events — kind-1 geo-notes, kind-31923 calendar events — precisely because relays index them; that rationale evaporates inside an encrypted DM.) The one real rule it illustrates: never move location onto the *outer* gift wrap (kind 1059) or seal (kind 13) — only the `["p", recipient]` routing tag belongs there, and anything sensitive must stay inside the encrypted kind-14.

What this means for us:

* *@mentions in group chats* (#1295) — the composer shows `@Name` and sends a NIP-27 `nostr:npub…` reference in the content. In a NIP-17 group that's all (no `p` tag, per the rule above); a Marmot group's kind 9 also `p`-tags each mentioned member (see <<marmot-protocol>>). Incoming `nostr:npub` / `nprofile` references inside a sentence render as `@Name` chips; a reference alone on its own line under a label is still a shared-contact card.
* *Mention and group-sender display names* (#1596) — `useMentionProfile` reads the signed-in profile first, then the shared `useNostrContacts` profile state and the screen's resolved Marmot member snapshot. The shared `cachedDisplayProfiles` reader also loads Messages' per-account `nonfollow_profiles` cache and saved local identity profiles before a relay query; Messages mirrors later batches into the cosmetic cache to notify existing consumers. Stale saved own profiles seed account state while the relay refresh runs, so a switch retains the display name even when relays miss. Marmot member lookups already populate `zapSenderProfileStorage`, which precedes the resolver's ten-minute memory cache. Misses share one active kind-0 batch (64 authors, six read relays, three seconds), followed by one bounded retry for unresolved authors on up to four write relays plus the two relay-list indexers. Focused consumers share ownership; the last blur aborts both attempts. Cache writes notify existing consumers through a 60 ms coalesced flush. These cosmetic names never supply verified payment fields.
* *Contact* — already done the interoperable way: `Shared contact: <name>\nnostr:<nprofile>` in the kind-14 content, `nprofile` carrying relay hints, recipient as the only `p` tag (`src/screens/ContactProfileScreen.tsx`, `extractSharedContact` in `MessageBubble.tsx`). No change needed.
* *Calendar event* — if we ever add "share an event to a DM", publish a NIP-52 kind-31923 and embed its `naddr` + a `q` tag; that interops with Amethyst's calendar for free.
* *Location / polls* — no interoperable card exists; the app-private encoding is the ceiling. A `g` geohash tag is *not* worth adding (encrypted inside the wrap → relays can't index it → no discovery, ~no rendering gain over the `geo:` URI); keep location in the kind-14 `content` and never on the outer wrap.

References: NIP-17 (DMs, allowed inner kinds 14/15/7), NIP-21 (`nostr:` URIs), NIP-27 (mentions in content; tags optional, only for notification), NIP-52 (calendar kinds + location tags), NIP-88 (polls, public-only). Cross-checked against `vitorpamplona/amethyst` `quartz` (`nip17Dm`, `nip52Calendar`, `nip19Bech32`).

=== Hunt: Lightning extension to NIP-GC (#468)

==== Summary

Lightning Piggy's "Hunt" feature lets users hide LNURL-withdraw "Piggies" in
the wild and lets others find + claim them. The wallet-level LNURL-w is
created by the hider in their own wallet (LNbits / Alby / Mutiny / …) — see
the project memory `No LNbits-specific APIs`. Lightning Piggy is the
**publisher**, **discoverer**, and **find-log thread** layer.

We adopt **NIP-GC** (Nostr Geocaching, draft by https://treasures.to[treasures.to])
verbatim and mark Lightning-payout caches with a **NIP-32 label**
(`L=com.lightningpiggy.app` / `l=payout-lnurl-w`). The LNURL bearer
token is deliberately **never** put on the public event — it lives
only on the physical NFC tag / QR and the hider's local SecureStore;
publishing it on a kind 37516 would let any relay subscriber drain
the cache without ever physically visiting it (see
`feedback_lnurl_never_on_relays.md` and the
`buildCacheListing` security test in `nostrPlacesService.test.ts`).
A Hunt Piggy is therefore just a NIP-GC `traditional` cache flagged
by our label; generic geocaching clients (treasures.to et al.)
ignore the label and render it as a normal cache, while Lightning Piggy routes
the finder through HuntFoundScreen for claim. The `wait` / `uses`
fields exist on the local `HiddenPiggy` record for the cooldown UX
but are NOT published as event tags — that was an early design
draft that got dropped to avoid side-channel discoverability of
the cache's economics. **Read the
upstream draft** in the kind-30817 event with `d="geocaching-events"`
authored by `npub1pse...zz68` (or
https://nostrhub.io/naddr1qvzqqqrcvypzppscgyy746fhmrt0nq955z6xmf80pkvrat0yq0hpknqtd00z8z68qqgkwet0vdskx6rfdenj6etkv4h8guc6gs5y5[the
nostrhub.io rendering]).

The data model uses **three Nostr kinds with three different lifecycles**:

[cols="1,1,1,3", options="header"]
|===
| What | Kind | Lifecycle | NIP source

| Cache listing | `37516` | **Replaceable** (PRE — `30000-39999` range, keyed by `(pubkey, kind, d)`). Hider can re-publish to update LNURL, location, hint, cooldown, expiry, etc.; relays drop the prior version. | NIP-GC §"Geocache Listing Event"
| Found-log entry | `7516` | **Append-only**, `7000-7999` regular range. Each find produces one event tagged to the cache's `a` coordinate. Optional embedded `kind 7517` verification event for cryptographic find-proof. | NIP-GC §"Found Log Event"
| Comment / status (DNF, note, maintenance, archived) | `1111` | **Append-only**, NIP-22 comment threading model with the cache as both root + parent. | NIP-GC §"Comment Log Events" + NIP-22
|===

==== kind 37516 listing — full tag schema

NIP-GC required tags (we always emit):

[cols="1,3", options="header"]
|===
| Tag | Meaning

| `["d", piggy_id]` | Stable identifier scoped to the hider's pubkey. Format: `piggy_<base36-millis>_<random6>` (see `newPiggyId` in `src/services/piggyStorageService.ts`).
| `["name", str]` | Short human-readable cache name. Required by NIP-GC.
| `["g", geohash]` (×7) | Location at every precision from 3 to 9 chars — cheap on event size, dramatically widens prefix-filter surface for proximity queries. See `src/utils/geohash.ts`.
| `["D", "1-5"]` | Finding difficulty. We default `1` (just-find-the-tag) for NFC-stash Piggies; user can override for tricky hides.
| `["T", "1-5"]` | Physical terrain. Default `1` (urban/accessible); bump for hilltop / hike-required caches.
| `["S", "micro\|small\|regular\|large\|other"]` | Cache size. Default `micro` since an NFC sticker is small.
|===

NIP-GC optional tags (we emit when present):

[cols="1,3", options="header"]
|===
| Tag | Meaning

| `["t", "traditional\|multi\|mystery"]` | Cache type. Default `traditional` per NIP-GC. **All Lightning Piggies are traditional caches with a Lightning bonus.**
| `["hint", rot13(str)]` | Plaintext clue, ROT13-encoded per NIP-GC client guidance (prevents inline spoilers in scrolling clients). Lightning Piggy decodes for display; users with non-NIP-GC-aware clients see the rotated text and need to ROT13 themselves.
| `["image", url]` | EXIF-stripped Blossom / nostr.build URL of the hider's hint photo. Routed through `src/services/imageUploadService.ts`.
| `["expiration", unix_ts]` | NIP-40. Clients hide the listing past this time without needing a separate delete event.
|===

Lightning Piggy marker tags (NIP-32 label, **not** a bearer token — the LNURL deliberately does NOT go on the public event):

[cols="1,3", options="header"]
|===
| Tag | Meaning

| `["L", "com.lightningpiggy.app"]` | NIP-32 label namespace declaring "this cache is in the Lightning Piggy taxonomy".
| `["l", "payout-lnurl-w", "com.lightningpiggy.app"]` | NIP-32 label value within the namespace — declares the cache pays out via LNURL-withdraw on the physical artifact (the NFC tag / printed QR carries the actual LNURL string). Generic NIP-GC clients (treasures.to) ignore the label entirely and render the cache as a standard listing; Lightning Piggy recognises it and renders the 🐷 pin + "tap the physical tag to claim" UX.
|===

**The LNURL never goes in the public event** — that would broadcast a bearer token to every relay subscriber, letting anyone in the world drain the cache without ever physically visiting it (defeating the entire physical-cache premise). The LNURL lives on:

* The **physical artifact** (NFC tag / printed QR) — this is the real access control. Possession = consent to claim.
* The **hider's local `SecureStore`** (`piggyStorageService.HiddenPiggy.lnurlw`) — for tag-write, re-print, and any future "show me the QR for this Piggy" affordance. Never leaves the device.

This is how TapTheSatsMap (the most prolific NIP-GC publisher, 31 sticker caches) operates — see project memory `treasures.to interop` for the analysis. Wait_time / uses / per-claim caps remain the hider's responsibility to set in their own wallet's LNURL-w configuration; Lightning Piggy doesn't try to mirror them on the event because doing so contributes to side-channel discoverability of the cache's economics without adding any safety.

`content` carries the longer cache description ("🐷 Geo-Cache 1 — 21 sats per claim, 3h cooldown, 100 uses.").

==== kind 7516 found-log — what we emit

Each successful claim produces:

* `["a", "37516:<hider_pubkey>:<piggy_id>"]` — required NIP-GC reference to the cache.
* `["image", url]` (optional) — finder's photo of the find spot. Same EXIF-strip pipeline as the listing's hint photo.
* `["amount", "21"]` (Lightning Piggy extension) — sats claimed via the LNURL-w. Drives the `⚡ claimed` badge and "you got 21 sats here 47m ago" copy on the detail screen. Treasures.to et al. ignore this; for them it's a regular found-log.
* `["verification", <kind-7517-json>]` (optional) — embedded NIP-GC verification event signed by the cache's verification key, if the listing carries one. **For Lightning Piggy Piggies we don't need this** — successful claim of the LNURL-w is its own physical-presence proof (you had the bearer token, the issuer paid you).

==== Subscribe filter shape

* **Discovery feed** — `{ kinds: [37516], "#g": [<geohash prefixes for current viewport>] }`. Single round-trip catches both Lightning Piggy Piggies AND treasures.to caches in the same area (we filter for the `["l", "payout-lnurl-w", "com.lightningpiggy.app"]` label client-side to render the 🐷 vs 📍 pin distinction). Prefix list comes from `geohashPrefixes(currentGh, 5)` so one subscribe covers a ~5 km city neighbourhood.
* **Single cache detail (replaceable + thread)** — three filters:
  ** `{ kinds: [37516], authors: [hider], "#d": [piggy_id] }` — latest revision of the listing.
  ** `{ kinds: [7516], "#a": ["37516:<hider>:<piggy_id>"] }` — append-only found-log thread.
  ** `{ kinds: [1111], "#A": ["37516:<hider>:<piggy_id>"] }` — append-only comment thread (DNF / notes / maintenance / archived).
* **My Piggies (cross-device)** — `{ kinds: [37516], authors: [me] }` and filter the result for the NIP-32 `["l", "payout-lnurl-w", "com.lightningpiggy.app"]` label marker. **Not** the `lnurl` tag — that one deliberately never reaches the relay (see the "marker tags" subsection above).

==== Why NIP-GC rather than a custom kind

We initially picked a custom `kind 30408` (still in the PRE range, semantically equivalent). Switched to NIP-GC `kind 37516` after a one-line user direction:

> _"i think we should use their NIPs and use traditional but with an LNUrlw additional field."_

Reasons it's the right call:

* **Network effects.** treasures.to users see our Piggies on their map, vice versa. One geocaching ecosystem on Nostr instead of two competing ones.
* **No semantic conflict.** A Lightning Piggy *is* a traditional NFC-tag cache — it just also pays. The `lnurl` extension is purely additive; their schema doesn't need to change.
* **Their schema is more thought-through.** D/T/S/t classification, ROT13 hint convention, NIP-22 comment-thread model, optional cryptographic verification (kind 7517) all generalise beyond what we'd built. We inherit it for free.
* **Migration cost: trivial.** `30408` → `37516` is a single-kind change; the tag schema is a strict superset of what we had; one orphan test event from the old kind hits its 30-day NIP-40 expiration and ages out.

==== `lightning:` tag-tap / deep-link routing

An NFC tag tap, a QR scan, or a `Linking` call from another app wakes
Lightning Piggy via the `lightning:` scheme (registered in `app.config.ts`).
The single handler in `App.tsx`'s Linking listener decides the *direction*
of money flow and routes to the matching surface. There are two directions:

* **Claim FROM** (money *in*): an LNURL-withdraw voucher → the withdraw
  claim flow (`HuntFoundScreen`). Introduced in #341 / #468.
* **Pay TO** (money *out*): an invoice, Lightning Address, or LNURL-pay
  endpoint → the `SendSheet` on the Wallets tab. Introduced in #756.

The critical rule: for LNURL forms the direction is keyed off the
**resolved `tag`** (`payRequest` vs `withdrawRequest`), *never* the bech32
prefix — a `lnurl1…` can be either kind. `resolveLnurlDirection`
(`src/services/lnurlService.ts`) does one fetch and returns
`{ kind: 'pay' | 'withdraw', … }`; both directions branch on that one
answer so they can never disagree.

|===
| Tapped / scanned payload | Spec | Direction | Routes to

| `lightning:lnbc…` (also `lntb` / `lnts` / `lnbs`) | BOLT-11 | Pay → out | `SendSheet` prefilled (amount + memo from the invoice; zero-amount invoices prompt for an amount)
| `lightning:user@host` | LUD-16 | Pay → out | `SendSheet` — resolves the address, prompts for an amount
| `lightning:lnurl1…` / `lnurlp://` / `https://…` resolving to `payRequest` | LUD-06/17 | Pay → out | `SendSheet`
| `lightning:lnurl1…` / `lnurlw://` / `lnurl://` resolving to `withdrawRequest` | LUD-03 | Claim → in | `HuntFoundScreen` (no regression to #341)
| anything else under `lightning:` | — | — | friendly "Link not supported" toast (no silent dead end — Copilot review #488)
|===

Cold launch is handled the same way as the withdraw and notification
paths: each route returns a boolean "did it land", and the handler retries
(~2 s, 100 ms cadence) until `navigationRef.isReady()`.

NOTE: The `payRequest → SendSheet` leg currently passes the resolved
endpoint URL to `SendSheet.processInput`, which today only decodes bolt11
and Lightning Addresses. Teaching `processInput` to also resolve a raw
LNURL-pay endpoint is the remaining wiring (tracked in #756); the bolt11
and Lightning-Address pay legs are fully wired.

=== Deep-link & NFC tag-tap routing

==== Summary

A scanned NFC tag (Android system NDEF dispatch) and a tapped deep link both arrive at the same place: the `Linking` handler in `App.tsx` (`getInitialURL()` for cold launch + `addEventListener('url')` for warm). The handler inspects the URI scheme / bech32 prefix and routes to the matching in-app surface. Every branch retries against `navigationRef.isReady()` so a cold-start tap that races the nav tree's mount still lands. Unknown payloads get a friendly toast or the `UnsupportedEntity` screen — never a crash or a blank screen.

Android registration is twofold: the `VIEW` intent filters in `app.config.ts` (`android.intentFilters`) wake the app on a deep link / cold launch, and the `NDEF_DISCOVERED` filters in `plugins/withNfc.js` route a foreground/background tag tap. ==== npub vs nprofile (read + write)

`npub` is the bech32 of the bare 32-byte pubkey — identity only. `nprofile` is the NIP-19 TLV encoding of the pubkey **plus optional relay hints**. For a conference badge / contact tap (cold first contact — the scanner doesn't follow the owner yet) `nprofile` is strongly preferred: the embedded hints let the scanner's client find the owner's kind-0 metadata + notes even on niche relays, where a bare `npub` would force a default-relay guess and could render a blank profile.

* **Read (#754):** the `App.tsx` router decodes the reference via `decodeProfileReference` (`src/services/nostrService.ts`), fetches kind-0 off the embedded hints (`fetchProfile(pubkey, hints)` — a bare `npub` carries none, so it falls back to the app's `PROFILE_RELAYS`), and navigates to `ContactProfile`. The fetch races a short budget so a dead relay never strands the user; the pubkey-only stub lets `ContactProfileScreen` retry on the viewer's own relays. Pure decode / shaping helpers are in `src/utils/nostrProfileLink.ts`.
* **Write (#755):** the "share my profile to NFC" path (`ProfileScreen` / `AccountDrawerContent` → `NfcWriteSheet`) writes `nostr:nprofile1…`, embedding the user's NIP-65 **write (outbox)** relays via `buildOwnProfileRelayHints` (`src/services/nostrService.ts`), capped at 2 to fit an NTAG213 (~144 B) and limit staleness. Falls back to the app defaults when the user has no published write relays — a generic hint still beats none. The bare pubkey is always embedded, so a reader can fall back to outbox discovery if the hints go dead. Sharing a *contact's* profile (`ContactProfileScreen`) writes their `nprofile` too, hints sourced via `buildProfileRelayHints`.
