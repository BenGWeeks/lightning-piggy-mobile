= Marmot interop suite (Lightning Piggy ↔ White Noise)

A replayable check that Lightning Piggy's Marmot (MLS) chats interoperate
with White Noise. One run covers the matrix in minutes, holding a device lock
only while Maestro is driving.

== How it works

. *Scripted sender, no UI.* `scripts/interop/marmot-sender.mjs` signs in as a
  test Piggy (Middle by default) on its *own* MLS device, creates a fresh group
  `IO <tag>` and invites every Lightning Piggy install of Big Piggy and Little
  Piggy's White Noise in one commit (the multi-device path, #1239). It then
  sends the item set from `scripts/interop/items.mjs`: the text set (plain,
  Chinese, emoji, Markdown, JSON, JavaScript, HTML, a long post, a 300-letter
  word, zero-width/RTL/Zalgo), a reply, two reactions and an un-react, an edit,
  a delete, an image and a voice note (MIP-04, on White Noise's Blossom
  servers), an invoice (an *expired* 21-sat test invoice — never payable), a
  location and a contact card. It also opens a Marmot 1:1 with Big for the
  reply/reaction subset, since Lightning Piggy has no reactions in groups yet.
. *Maestro verifies on screen*, one labelled, `optional` check per item, so a
  missing item doesn't hide the rest. Every message carries the run's marker
  `IO<tag> <item>`, so a check can never pass on a leftover bubble.
. *Lightning Piggy → White Noise:* Lightning Piggy sends its own items through
  the real UI (flow-147). The scripted member confirms they arrived on the
  wire (`listen`), and White Noise confirms they render (flow-148).
. *Membership/metadata changes:* the sender makes Big an admin, Lightning
  Piggy renames the group and sends straight away (the #1309 path), and both
  apps are checked for the post-change messages.

|===
| Flow | Device app | Checks

| `flow-145-interop-lp-receives-group` | Lightning Piggy | every sender item in the group
| `flow-146-interop-wn-receives-group` | White Noise | every sender item in the group (accepts the invite)
| `flow-147-interop-lp-sends-group` | Lightning Piggy | sends text, edit, delete, photo
| `flow-148-interop-wn-receives-lp` | White Noise | Lightning Piggy's items + post-rename/admin messages + new name
| `flow-149-interop-lp-rename-after-admin` | Lightning Piggy | sees the admin-change message, renames, sends
| `flow-150-interop-lp-receives-after-rename` | Lightning Piggy | receives after its own rename
| `flow-151-interop-lp-receives-dm` | Lightning Piggy | reply quote, reactions, un-react, edit, delete in a Marmot 1:1
|===

Shared building blocks: `common/interop-lp-open-chat.yaml` (opens a chat by
its exact Messages-row testID) and `common/interop-wn-open-chat.yaml` (opens
the run's group in White Noise by its exact name and accepts the invite).

== Running it

Prerequisites on the device (default `emulator-5554`):

* Lightning Piggy dev client signed in as *Big Piggy*.
* White Noise (`dev.ipf.whitenoise.android`) signed in as *Little Piggy*, and
  that account active (White Noise supports several accounts; an invite for
  another account switches it).
* `.env` with `MAESTRO_NSEC_BIG`, `MAESTRO_NSEC_MIDDLE`, `MAESTRO_NSEC_LITTLE`.
* Maestro on `PATH`, `jq`, Node.

[source,bash]
----
bash scripts/interop/run.sh
# against a branch bundle on your own Metro (restored to 8090 afterwards):
METRO_PORT=8271 bash scripts/interop/run.sh
# Lightning Piggy only:
SKIP_WN=1 bash scripts/interop/run.sh
# another lane (its own lock), waiting up to 2 h for a busy lane:
DEVICE=127.0.0.1:5565 DEVICE_LOCK=/tmp/claude-$UID/hulk-emu.lock LOCK_WAIT=7200 \
  bash scripts/interop/run.sh
----

Output: `~/lp-interop-runs/<date>-<tag>/` with `matrix.md`, `screenshots/` and
`logs/` (Maestro output and the sender's JSON lines, nsecs redacted). The
matrix separates harness problems from interop results: a flow that fails
before its first check is reported as `HARNESS: no results` with the failing
step, and checks that depend on a flow that didn't run (Lightning Piggy's
sends, its rename) are `N/T`, not FAIL.

Locks: the runner holds `$LOCK_DIR/emulator.lock` (default
`/tmp/claude-$UID`) for two windows (sender items + checks, then the
admin/rename checks) and releases it in between, with `maestro.lock` taken per
flow inside it. The sender acts *inside* the device lock on purpose: if
another build of Lightning Piggy is running on the device while it sends (for
example the lane's default Metro bundle), that build joins the group and
consumes the MLS messages. They're one-time secrets, so the bundle under test
could never show them. Each window points the app at the run bundle and stops
it before the sender acts.

The sender is also useful on its own, e.g. to poke an existing group:

[source,bash]
----
source .env && export INTEROP_NSEC=$MAESTRO_NSEC_MIDDLE
node scripts/interop/marmot-sender.mjs create --state /tmp/io.json --name "IO test" \
  --invite "<big hex>@Lightning Piggy,<little hex>@White Noise"
node scripts/interop/marmot-sender.mjs send --state /tmp/io.json --tag abcd --only text,reply,react
node scripts/interop/marmot-sender.mjs rename --state /tmp/io.json --name "IO renamed"
node scripts/interop/marmot-sender.mjs listen --state /tmp/io.json --seconds 60 --expect "hello"
----

== Safety

* Only the three Piggy test accounts are ever involved; groups are created
  fresh per run and opened by their exact id / name.
* Nothing is paid: the invoice is expired, and no zap or wallet action runs.
* The sender never contacts relay.damus.io, nos.lol or nostr.mom (they
  rate-limit-ban the dev machine's IP). It uses relay.primal.net,
  relay.snort.social and relay.ditto.pub, and Welcomes go to each invitee's
  kind-10050 inbox (minus those relays).
* Each run adds one group to every invited install of Big Piggy and to Little
  Piggy's White Noise. They're labelled `IO <tag>`.

== Known gaps and fragility

* *White Noise selectors are text-based* (third-party UI, no testIDs) and tied
  to its English copy and rendering in 2026.10.3: it renders Markdown and
  decodes HTML entities (checks match the marker only), and labels media by
  filename. A White Noise release can break them without any interop change.
* *Groups have no reactions or Reply in Lightning Piggy* (#1328), so the
  reaction checks in flow-145 are expected to fail until that ships; the 1:1
  flow (flow-151) covers reactions.
* *#1309*: after a Lightning Piggy rename or admin change, White Noise stops
  receiving. flow-148's `lp.after-lp-rename` / `lp.renamed-title` checks
  fail until it's fixed.
* Not covered yet: polls (White Noise has none), live location, leave /
  remove member, White Noise-initiated 1:1s and White Noise *sending* (its
  composer and long-press menus aren't in the accessibility tree; the
  scripted sender stands in for a White Noise peer on the wire), Amethyst.
* The checks swipe back through the thread (finger-down swipes, bounded) and
  return to the newest message after a miss; `scrollUntilVisible` was
  unreliable on Lightning Piggy's inverted chat list. `hideKeyboard` isn't
  used: on an emulator with a hardware keyboard it presses Back and leaves the
  chat.
* A flow is retried once if Maestro's on-device driver drops (gRPC
  `UNAVAILABLE`), which happens on busy lanes.
* Maestro's `inputText` is ASCII-safe only, so Lightning Piggy's own sends use
  ASCII; the Unicode text set runs in the sender → app direction.
* The sender's MLS state lives in `~/.cache/lp-interop-sender/<pubkey>`. If
  it's deleted, old run groups become unreachable for the sender (new runs
  are unaffected).
