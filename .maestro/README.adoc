= Maestro E2E test suite

Maestro flows in this directory run on the developer's AVD (and
sometimes their physical Pixel) against *real* Nostr relays under the
developer's *real* signed-in identity. There is no test relay or test
sandbox — anything a flow does will publish real events that real
contacts may see.

That makes selector hygiene a safety issue, not just a code-quality
issue. The rules below are enforced by hand on every PR that touches
this directory.

== Layout

Flows are organised one folder deep by feature area, mirroring the
Satmo suite. Composed end-to-end flows are named `flow-NNN-<description>`
with a globally-sequential number; the shared building blocks under
`common/` keep descriptive names (they are run via `runFlow`, never
on their own).

[source]
----

  authentication/      flow-NNN  login (dev/amber/perf), logout, create-account,
                       key import, cold-start isolation, signer matrix
                       (131 Amber setup, 132 smoke, 135 NIP-46 pairing timeout)

  friends/             flow-NNN  follow/unfollow, contacts, alphabet, search

  messaging/           flow-NNN  1:1 DM, conversation, attach panel, secret mode,

                       signer matrix: 133 Marmot Big (nsec) ⇄ Middle (Amber),
                       134 NIP-17 via NIP-46 (approve / decline / timeout)

Run one flow:

[source,bash]
----

== Piggy-only fixtures (group membership)

Any flow that *creates*, *adds members to*, *removes members from*, or
otherwise mutates a Nostr group MUST scope its member-targeting
selectors to the three Piggy test accounts and no others. A wildcard
like `text: 'Remove .*'` or `id: 'member-row-.*'` could happily remove
the developer's real friend from a real group, send a DM to a stranger,
or otherwise leak test activity outside the controlled fixture set.

The three Piggy accounts and their `member-row` / `group-member-remove`
testID suffixes (first 12 hex chars of the pubkey, matching the
`pubkey.slice(0, 12)` slicing in `CreateGroupSheet.tsx` and
`GroupMembersSheet.tsx`):

|===
| Account      | testID suffix    | Notes

| Big Piggy    | `ccedbff9a6f2`   | Default `MAESTRO_NSEC_BIG`. Usually the
                                    logged-in user, so doesn't appear
                                    in the *other* members list — appears
                                    in `group-member-row-*` (with a
                                    "· you" tag) but NOT in
                                    `group-member-remove-*`.
| Middle Piggy | `4b2fcb4e3c30`   | `MAESTRO_NSEC_MIDDLE`.
| Little Piggy | `d9b33280ba73`   | `MAESTRO_NSEC_LITTLE`. The default
                                    `MEMBER_PUBKEY_PREFIX` for the
                                    `groups/flow-025-create-leave-group.yaml` flow.
| Evil Piggy   | `0b747589`       | `MAESTRO_NSEC_EVIL`. Used as an
                                    untrusted/non-followed sender in
                                    follow-gate / spam-filter coverage.
|===

The "Triad" fixture group (created by
`groups/flow-022-3way-group-create-as-big.yaml`) has all three Piggies as members
and is the canonical group to drive any member-mutation flow against.

=== Selector rules

Do:

* `id: 'member-row-d9b33280ba73'` — full Piggy testID
* `id: 'group-member-remove-d9b33280ba73'` — full Piggy testID
* `id: 'member-row-${MEMBER_PUBKEY_PREFIX}'` — env var, with the
  comment in the flow stating that the default + accepted values are
  Piggy prefixes only
* `text: 'Triad'` — exact, known fixture group name
* `text: 'Open group Triad'` — accessibility-label exact match

Don't:

* `text: 'Remove .*'` — matches any member's X button, including real
  friends
* `id: 'member-row-.*'` — matches any contact in the picker
* `text: 'Open group .*'` — opens whichever group happens to be at the
  top, which on a real signed-in device is whatever the user's most
  recent group activity is
* `text: '.* members'` — same problem
* Any other regex / substring that could resolve to a non-Piggy member
  or non-fixture group

=== When a flow can't use a Piggy prefix

If a flow needs to exercise a code path the Piggies can't cover (e.g.
something specific to a profile-card layout that only renders for a
non-Piggy contact), the flow MUST be gated behind a `runFlow when:`
clause that asserts a Piggy fixture is present, OR explicitly documented
at the top of the file as "manual run only — do NOT add to run-all.sh".
Don't ship an unguarded flow that taps a non-Piggy member.

== Signer matrix (nsec / Amber / NIP-46)

The same LP install is exercised with each of the app's three Nostr signers,
one Piggy per signer:

|===
| Piggy        | Signer | Where the key lives

| Big Piggy    | `nsec` (local key) | LP's SecureStore — the device default
| Middle Piggy | Amber (NIP-55, Android Intent IPC) | Amber on the emulator (`flow-131` imports it)
| Little Piggy | NIP-46 (Nostr Connect) | `scripts/nip46-test-bunker.sh` on the host
|===

`bash scripts/signer-matrix-e2e.sh` runs flows 132–134 (add `135` for the
slow pairing-timeout case, `setup-amber` once per fresh Amber install). It
starts/stops the bunker, tags every message with a per-run `RUN_TAG`, prints
how many Amber prompts each flow had to answer (a prompt-storm signal) and the
bunker's per-method request counts, and keeps screenshots + a redacted copy of
Maestro's debug output under `$OUT`.

* *Identities are switched, not wiped.* The building blocks never
  `clearState` (that wipes the dev client's bundle URL and every account's
  wallets and Marmot state). They use LP's account switcher: Middle / Little
  are signed out of the registry first (`common/forget-piggy.yaml`) so they
  always start clean with the signer under test, and every flow ends with Big
  Piggy active and Middle / Little signed out again.
* *NIP-46 isn't in the account registry* (`useNip46Login.ts`), so Little is
  added on top as the active session and handed back with
  `common/sign-out-nip46-little.yaml` — which refuses to sign out anyone but
  Little.
* *Amber is a third-party app*: `common/amber-import-key.yaml` and
  `common/approve-amber-prompt.yaml` use Amber's own English copy as text
  selectors ("Use your private key", "Connect", "Accept", "Reject",
  "Approve" / "Confirm" on its batched-requests sheet — Amber v6.6.7), and
  only while Amber's prompt is on screen (it prints the requesting app id,
  `com.lightningpiggy.app.dev`, which LP's own UI never shows). No
  coordinates anywhere.
* *The bunker is driven from the flow*: `common/nip46-bunker.js` (via
  `runScript`) flips its mode (`approve` / `decline` / `silent` / `-all`
  variants), answers LP's pairing QR (the bunker screencaps the device and
  decodes it — the pairing secret never leaves the host) and asserts its
  request counters.
* *Two LP sheets ignore Back or get stuck* (the Accounts sheet, and the DM
  protocol picker — #1164). `common/close-sheets.yaml` /
  `common/close-protocol-picker.yaml` swipe them down from their title text:
  an element-anchored `swipe: { from: … }`, not a coordinate.

=== Secrets in signer-matrix flows

* nsecs reach Maestro only through the environment: the runner exports just
  `MAESTRO_NSEC_{BIG,MIDDLE,LITTLE}` (nothing else from `.env`) and Maestro
  picks up `MAESTRO_*` itself — no `-e MAESTRO_NSEC_…=` on the command line,
  where `ps` can see it. Run the matrix through `scripts/signer-matrix-e2e.sh`;
  to run one flow by hand, export those three the same way, plus
  `MAESTRO_NIP46_TOKEN="$(cat "$(bash scripts/nip46-test-bunker.sh token-file)")"`
  for the NIP-46 flows.
* Every `inputText` of an nsec carries a `label:`, so Maestro's console shows
  "Enter the Piggy nsec (redacted)" instead of the key.
* Maestro's debug output (`~/.maestro/tests/<run>/commands-*.json`,
  `maestro.log`) still records the *evaluated* command, nsec included, and
  its environment (the bunker token). The runner sends it to a private temp
  dir, redacts `nsec1…` and the token, drops the automatic screenshots of the
  NIP-46 flows (one could show the pairing QR, which carries the pairing
  secret) and discards it entirely if redaction fails. If you run these flows
  by hand, pass `--debug-output` to a temp dir and delete it afterwards.
* The bunker reads Little's nsec from `.env` with `grep` and hands it to node
  on stdin — never argv, the environment, its state dir or its log.

== Other safety conventions

* Never use coordinate taps (`point:`, `tapOn: { point: }`,
  `adb shell input tap`). See `CLAUDE.md` § Testing. A swipe anchored on an
  element (`swipe: { from: { text: … }, direction: DOWN }`) is fine.
* Never send a real Lightning payment from a flow. Use lightning
  addresses that don't resolve (`test@example.com`) or invoices the
  flow generates and then cancels.
* Never tap "Confirm" / "Send" on a payment, contact-share, or DM
  unless the recipient is another Piggy.

== Settings restructure (#1222)

`flow-072-secret-mode.yaml` enables the visible Secret Mode switch in Advanced
→ Developer options and accepts its confirmation. It intentionally leaves the
mode enabled for wallet-import flows. `flow-094-account-drawer.yaml` checks
cancellation and enable/disable while preserving the initial mode. Neither
flow uses the About version label anymore. Invitation keys will belong in
Settings → Messages when that screen is available.
